**NAT를 HA로 (2 AZ) 구성하면 +$43** 이다. 이 시스템은 관측 도구이고 NAT 장애 시
수집이 멈추지만 관측 대상에는 영향이 없다. → **단일 AZ NAT로 시작**하고, NAT 장애가 실제
문제가 되면 그때 이중화한다.

**VPC 인터페이스 엔드포인트는 기본적으로 두지 않는다.**
9종을 2 AZ에 두면 `9 × 2 × 730 × $0.013 ≈ $171/월` + GB당 요금이다.
NAT($55)보다 비싸다. **저트래픽 서비스에서는 엔드포인트가 손해**다.
- 무료인 **게이트웨이 엔드포인트(S3, DynamoDB)만** 둔다.
- 인터페이스 엔드포인트는 트래픽이 큰 것 하나씩 손익분기(GB × $0.059 NAT vs 시간당 $19)를

- **엔드포인트는 리전 로컬이다.** 멀티 리전 대상의 `rds:Describe*`·`GetMetricData`·
  `FilterLogEvents`는 원격 리전 퍼블릭 엔드포인트로 나가므로 **여전히 NAT를 탄다.**

### 2.6 Athena — $6/월

| 용도 | 스캔량 | 월 비용 |
|---|---|---|
| 아카이브 `MERGE INTO` (일 1회, **파티션 프루닝 적용**) | 일 약 2GB × 30 = 60GB | $0.3 |
| 월간 리포트 (환경 3 × 쿼리 15) | 회당 20GB × 3 = 60GB | $0.3 |
| 개선 리포트 (월 20건) | 건당 2GB = 40GB | $0.2 |
| UI 온디맨드 과거 조회 | 월 200회 × 5GB = 1TB | $5 |
| **소계 ($5/TB)** | | **$6** |

**⚠ `MERGE INTO`에 파티션 조건이 없으면 매일 대상 테이블 전량을 스캔한다.**
`ON t.record_id = s.record_id`만으로는 `record_id`가 파티션 키가 아니므로 프루닝이 불가능하다.
1년 170GB × 30일 = **월 5.1TB = $25**(추정의 140배). 더 심각하게,
**워크그룹 쿼리당 한도(10GB)에 걸려 아카이브 잡이 매일 실패**한다.

→ 두 가지를 함께 적용한다.
1. `MERGE` ON 절에 파티션 조건 추가:
   ```sql
   ON t.record_id = s.record_id
      AND t.started_at >= <증분구간_시작일>
      AND t.started_at <  <증분구간_종료일 + 1일>
   ```
2. **아카이브 전용 워크그룹**을 두고 per-query 한도를 별도로 설정한다(예: 100GB).
   사용자 조회 워크그룹과 한도를 격리해 서로 마비시키지 않게 한다(T-35).

**파티션 프루닝이 깨지면 여기가 폭발한다.** `TimeRange` 필수 인자
([12 §6](12-reporting.md))와 생성 SQL 정적 검사가 그 방어다.

**이 항목이 처음 완전히 빠져 있었다.** 대상 MySQL 폴링 트래픽은 무료가 아니다.

인스턴스 1대에서 우리가 받는 응답량(최적화 후, [05 §2.5.3](05-collector.md) 참조):

| 루프 | 주기 | 응답 크기 | 일 볼륨 |
|---|---|---|---|
| `detect` | 1초 | 약 100B (보통 0행) | 8.6MB |
| `digest` ① | 60초 | 약 120KB (300행 × 400B) | 173MB |
| `digest` ② (텍스트) | 신규 시에만 | 가변 | ~2MB |

| `daily` (테이블 통계 등) | 1일 | 약 5MB | 5MB |
| **합계** | | | **약 240MB/일 = 7.1GB/월** |

| 배치 | 단가 | 500대 월 비용 |
|---|---|---|
| 동일 리전 · 동일 AZ | $0 | $0 |
| 동일 리전 · 다른 AZ | **$0.01/GB 양방향** (송신 + 수신 각각) | — |
| 크로스 리전 | 소스 리전의 리전간 요율 (약 $0.02~0.09/GB) | — |

**혼합 시나리오** (350대 동일 리전 다른 AZ, 150대 크로스 리전):
```
동일 리전 다른 AZ : 350 × 7.1GB × $0.01 × 2방향  = $49
크로스 리전 (수신) : 150 × 7.1GB × 평균 $0.05     = $53
요청 방향 egress  : 약 3.5TB × 소액                = $20
                                            합계  ≈ $122
```

**초기 계산의 오류** — 크로스 AZ를 한 방향만 계산했다. AWS는 AZ 간 전송을
**송신 $0.01/GB + 수신 $0.01/GB 양방향** 과금한다.

**최적화 전이었다면** (`LAST_SEEN` 필터·컬럼 분리 없이 다이제스트 전량을 매분 조회)
인스턴스당 월 540GB → 500대 = 270TB/월. 크로스 리전이면 **월 수천~수만 달러**다.
[05 §2.5.3](05-collector.md)의 최적화가 비용 설계이기도 하다.

**크로스 리전 네트워크 패브릭 비용이 별도로 필요하다.**
위 계산은 데이터 전송료만이고, 그 트래픽을 흘릴 경로 비용이 빠져 있다.

| 방안 | 비용 | 제약 |
|---|---|---|
| **리전별 collector 배치** | 리전당 EC2 1대 (c7g.large $60/월) + DynamoDB 쓰기만 크로스 리전 | 배포 대상 증가. 리스·설정이 리전을 넘나듦 |
| 리전간 VPC 피어링 | 어태치먼트 무료 + 데이터 전송료 | **보안 그룹 참조 불가** → 대상 팀에 CIDR 허용을 요청해야 하고 승인 난도가 훨씬 높다 |
| Transit Gateway | 어태치먼트 $36.5/월/개 + 데이터 처리 $0.02/GB (3.5TB = $70) → **$150~250/월** | 가장 비싸다 |

→ **크로스 리전 대상이 20대를 넘으면 리전별 collector 배치가 가장 싸다.**
[OPEN-Q-02](OPEN-QUESTIONS.md)의 결정은 지연뿐 아니라 이 비용 비교로 내린다.
Terraform 모듈 목록에 `network-peering`이 없는 것은 **의도적**이다 — 네트워크 패브릭은
조직 공통 인프라이므로 이 프로젝트가 소유하지 않는다. 필요한 요구사항만 문서화한다.

**VPC 엔드포인트는 MySQL 연결에 적용되지 않는다.** AWS 서비스 트래픽(DynamoDB, S3,
Secrets Manager)에만 해당한다.

## 5. 비용 관측 (NFR-O-03)

| Athena 스캔 바이트 (아카이브·리포트, 별도 워크그룹 `dbmon-batch`) | 동일 | 일 2GB (리포트일 62GB) | **일 300GB** | 알림만 (제한하면 아카이브가 멈춘다) |
| Bedrock 입력·출력 토큰 | Converse 응답 | 환경별 | **환경별 설정값** | 자동 실행 중단, 수동은 admin만 |
| DynamoDB 소비 용량 | CloudWatch `ConsumedWriteCapacityUnits` | 일 402만 | **일 800만** | 알림 + 롤업 상위 N 자동 축소 제안 (자동 축소는 하지 않는다) |
| S3 저장량 | Storage Lens | 200GB | **400GB** | 알림만 |
| 내보내기 바이트 | `DescribeExport` | 일 1.2GB | **일 5GB** | 알림만 |
| 데이터 전송 바이트 | VPC Flow Logs 또는 추정 | 월 3.5TB | **월 7TB** | 알림만 |

**"100% 도달 시 제한"이 가능한 것과 불가능한 것을 구분한다.**
CloudWatch·Athena·Bedrock은 요청을 거부하면 그만이지만, DynamoDB 쓰기는 거부하면
**데이터를 버리는 것**이다(NFR-R-06). 그래서 DynamoDB는 알림만 하고, 실제 축소는
사람이 설정을 바꿔야 한다.

- 예산의 80% 도달 → `platform.*_budget_pct` 알림 (info)
- 100% 도달 → 해당 기능 제한 모드 (CloudWatch: 캐시 강제, AI: 자동 실행 중단,
  Athena: 신규 쿼리 거부하고 캐시만)
- AWS Budgets로 태그(`Project=dbmon`) 기준 월 예산 알림을 별도로 설정한다.
  자체 계측이 틀렸을 때의 최후 방어선.

## 6. 재검토 시점

| 시점 | 확인할 것 |
|---|---|
| 배포 후 1주 | 실제 슬로우 쿼리·다이제스트 볼륨이 가정과 얼마나 다른가 |
| 배포 후 1달 | S3 Tables 실제 요금 구조, DynamoDB 쓰기 실측, Cognito 계층 |
| 배포 후 3달 | DynamoDB 프로비저닝 모드 전환 검토, Savings Plan 구매 |
| 배포 후 6달 | 상위 N 값이 적절한가 (커버리지 vs 비용), 어드바이저 캐시 히트율 |
| 인스턴스 300대 도달 | 워커 수·타입 재산정, 리전별 collector 배치 필요성 |

이 문서의 숫자는 **가정이다.** 실측 후 반드시 갱신하고, 갱신 이력을 남긴다.
