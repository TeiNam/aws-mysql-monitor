# 03. 기술 결정 기록 (ADR)

각 항목은 **결정 / 맥락 / 검토한 대안 / 근거 / 대가 / 재검토 조건** 순서다.
"대가"와 "재검토 조건"이 없는 결정은 결정이 아니라 취향이다.

## ADR-001. 백엔드 언어: Rust

**결정** — 백엔드 전체(수집기 + API + 스케줄러 + 알림 평가)를 Rust로 작성한다.
웹 프레임워크는 `axum`, 런타임은 `tokio`, MySQL 드라이버는 `mysql_async`.

**맥락** — 현재 인스턴스 100대, 2년 내 목표 500대+. 인스턴스당 1초 폴링이 기본.
팀에 Rust 실무 경험이 있다. 기존 PoC는 Python/FastAPI.

**검토한 대안**

| 대안 | 500대 규모 적합성 | 개발 속도 | 배포 | 판단 |
|---|---|---|---|---|
| **Rust (axum/tokio)** | 우수. 태스크당 오버헤드 수 KB, GIL 없음, 파싱·정규화가 CPU 병목이 되지 않음 | 느림(초기). 팀 경험 있으면 상쇄 | 단일 정적 바이너리 | **채택** |
| Go | 우수. goroutine 모델이 이 워크로드에 매우 적합, AWS SDK 성숙 | 빠름 | 단일 바이너리 | 차선. Rust 경험이 있다면 Rust가 유리 |
| Python asyncio (현행 유지) | 조건부. 500대면 워커 프로세스 4~8개로 샤딩 필수. 정규화·플랜 파싱에서 GIL 병목 | 가장 빠름, 기존 코드 재사용 | 컨테이너 + 다중 프로세스 | 기각 |
| Java/Kotlin (virtual threads) | 우수 | 보통 | JVM 튜닝 부담, 메모리 상시 사용량 큼 | 기각 |

**근거**
1. 진짜 병목은 I/O가 아니라 **CPU 쪽**이다. 인스턴스 500대 × 다이제스트 스냅샷(인스턴스당
   수백~수천 행 × 60초 주기) → 초당 수만 행의 파싱·정규화·해싱. Python은 여기서 GIL에 걸린다.
   측정 없이 단언하지 않기 위해 [OPEN-Q-01](OPEN-QUESTIONS.md)에 벤치마크 항목을 남긴다.
2. `information_schema.PROCESSLIST` 결과의 SQL 텍스트는 수 KB~수백 KB가 될 수 있다.
   정규화는 문자열 스캔이고, Rust는 이걸 할당 없이 처리할 수 있다.
3. 메모리 사용량이 예측 가능하다. 실시간 지표 링버퍼(500대 × 60분 × 20지표)와 다이제스트
   누산기를 메모리에 두는 설계([ADR-009](#adr-009-시계열-저장소를-도입하지-않는다),
   [ADR-010](#adr-010-다이제스트는-시간-롤업--상위-n으로-영속화한다))는 GC 없는 런타임에서
   훨씬 다루기 쉽다.
4. 단일 정적 바이너리 → EC2 배포가 `systemd` 유닛 하나로 끝난다.
5. AWS SDK for Rust는 이 프로젝트가 쓰는 서비스(RDS, CloudWatch, DynamoDB, S3, Athena,
   Secrets Manager, Bedrock Runtime, Cognito IdP, STS)를 모두 지원한다.

**대가**
- 초기 개발 속도가 Python 대비 2~3배 느리다. 특히 프롬프트·리포트처럼 반복 실험이 많은
  영역에서 체감된다. → 완화: 프롬프트와 리포트 쿼리를 **코드 밖 파일**(TOML/SQL)로 빼서
  재컴파일 없이 수정 가능하게 한다.
- 기존 Python 자산을 재사용하지 못한다. 단 재사용 가치가 있는 건 SQL 문장과 설계 아이디어
  뿐이고, 그건 언어와 무관하게 이식된다.
- `mysql_async`의 IAM 인증 토큰 연동을 직접 배선해야 한다(SDK가 대신 해주지 않음).

**⚠ 이 근거는 아직 측정되지 않았다** — 근거 1("CPU가 병목")은 추론이다. 실제 병목은
500개 원격 DB 호출과 AWS I/O일 가능성이 크고, 그렇다면 언어 선택의 성능적 필연성은 약해진다.
정직하게 말하면 **Rust를 택하는 확실한 근거는 성능이 아니라 다음 세 가지**다:

1. **단일 정적 바이너리** — EC2 배포가 systemd 유닛 하나로 끝난다(런타임·의존성 설치 없음).
2. **메모리 예측성** — 링버퍼·누산기를 메모리에 두는 설계에서 GC가 없는 쪽이 다루기 쉽다.
3. **팀 역량** — Rust 실무 경험이 있다. 이게 없으면 이 결정은 성립하지 않는다.

성능은 "충분함이 확인되면 좋고, 아니면 대안이 필요한 항목"이며 M1-9에서 측정한다.
[ADR-010](#adr-010-다이제스트는-시간-롤업--상위-n으로-영속화한다)의 `LAST_SEEN` 필터가
파싱 대상을 100배 줄였으므로, 그 후에는 Python으로도 될 가능성이 있다.
그래도 위 1~3 때문에 결정을 되돌리지 않는다. **근거를 성능에 걸지 않는 것이 정직하다.**

**재검토 조건** — 개발 속도가 실제로 일정을 위협하면 수집기만 Rust로 남기고 나머지를 되돌린다.
M1-9 결과가 어떻든 위 1~3은 유효하므로, 이 조건은 성능이 아니라 **개발 속도**로만 발동한다.

## ADR-002. 단일 바이너리, 역할은 런타임 플래그로 분리

**결정** — `dbmon` 하나로 빌드하고 `--role api|collector|control`로 역할을 정한다.
기본값은 전부 한 프로세스.

**검토한 대안** — (a) 서비스별 별도 바이너리/저장소, (b) Lambda 함수 분해,
(c) 단일 바이너리 + 플래그.

**근거**
- 도메인 타입이 프로세스 경계를 넘지 않으므로 직렬화 계약과 버전 스큐가 없다.
- 소규모(≤150대)에서는 프로세스 1개로 충분한데, 처음부터 서비스를 쪼개면 운영 대상만 늘어난다.
- Lambda 분해는 1초 폴링과 상시 MySQL 연결 풀 유지에 맞지 않는다(콜드 스타트, 연결 폭주).

**크레이트 분리는 처음부터 다 하지 않는다** — 초기 설계는 크레이트 11개를 그렸다.
프로덕션 구현이 각각 하나뿐인 경계에 trait·DTO·변환·mock을 만들면 작은 팀이 수집 로직보다
구조 유지에 시간을 더 쓴다. → [02 §3](02-architecture.md)을 **4개**로 줄였다.

**M0에서 만드는 크레이트는 4개다.**

| 크레이트 | 이유 |
|---|---|
| `normalize` | 순수 함수. 골든 코퍼스 프로퍼티 테스트가 여기에만 필요. 의존성 0 |
| `planparse` | 순수 함수. fuzz 대상. 의존성 0 |
| `core` | 도메인 타입 + 포트 trait. 테스트용 페이크가 "두 번째 구현"이므로 trait이 정당 |
| `dbmon` | 나머지 전부 (bin). 내부는 평범한 Rust 모듈로 나눈다 |

`collector`/`api`/`awsinfra`/`alerting`/`advisor`/`reporting`/`scheduler`는 **`dbmon` 안의
모듈로 시작**한다. 파일당 400줄 상한(NFR-M-01)은 모듈로도 지킬 수 있다.
독립 배포가 필요해지거나 컴파일 시간이 문제가 되면 그때 크레이트로 승격한다.

`core`의 포트 trait을 M0에 두는 이유는 **테스트가 실제 두 번째 구현**이기 때문이다.
AWS·MySQL 없이 도메인 로직을 테스트하려면 경계가 필요하고, 그건 처음부터 있어야 한다.
그 외 경계는 지금 필요하지 않다.

**대가** — 한 역할의 메모리 누수/패닉이 다른 역할에 영향을 줄 수 있다.
→ 완화: 역할별 태스크 격리 + `JoinHandle` 감시, 2단계에서 실제로 분리 배포.
`dbmon` 크레이트가 커지면(파일 100개 이상) 컴파일 시간이 개발 속도를 해친다 → 그때 분리.

**재검토 조건** — API 트래픽과 수집 부하의 스케일 축이 실제로 달라지면 2단계 토폴로지로 이행
([02-architecture.md §8](02-architecture.md)).

## ADR-003. 핫 저장소: DynamoDB (MongoDB 대체)

**결정** — 최근 31일 데이터는 DynamoDB에 저장한다. 테이블 2개(`dbmon-data`, `dbmon-config`),
온디맨드 과금, PITR 활성.

**검토한 대안**

| 대안 | 판단 |
|---|---|
| **DynamoDB** | 채택. 운영 0, 자동 확장, TTL 내장, PITR 증분 내보내기로 아카이브 파생 가능 |
| MongoDB 유지(Atlas/self-hosted) | 기각. 자체 운영 부담이 1세대의 실제 통증이었다. Atlas는 비용·VPC 피어링 부담 |
| Aurora PostgreSQL | 유력한 대안. 집계 SQL이 공짜로 따라오고 파티셔닝으로 보관도 해결된다. 하지만 인스턴스 상시 비용 + 스키마 마이그레이션 운영이 생긴다. 이 워크로드는 쓰기 편중 + 키 기반 조회가 주력이라 관계형 이점이 크지 않다 |
| OpenSearch | 기각. 전문 검색은 매력적이지만 클러스터 운영 부담이 MongoDB와 다르지 않고 비용이 더 크다 |
| Timestream | 기각. 슬로우 쿼리 레코드는 시계열이 아니라 이벤트 문서다 |

**근거** — 접근 패턴이 5개로 명확하고([04-data-model.md](04-data-model.md)) 모두 키 기반이다.
집계는 콜드 티어(Athena)가 담당하므로 핫 티어에 SQL이 필요하지 않다.

**대가**
- 애드혹 쿼리가 안 된다. 새 조회 패턴이 생기면 GSI를 추가해야 한다.
- 항목 400KB 한도 때문에 큰 플랜은 S3 오프로드 분기가 필요하다.
- 전문 검색(SQL 텍스트 부분 일치)이 불가능하다. → 필터는 다이제스트·스키마·계정 기준으로
  제공하고, 텍스트 검색은 Athena 경로로 넘긴다. [OPEN-Q-08](OPEN-QUESTIONS.md)

**DynamoDB로 할 수 없는 조회를 명시한다** — 키 기반이 아닌 조회는 이 저장소로 안 된다.
MVP API를 실제 지원 가능한 것으로 **제한**하고, 나머지는 Athena 경로로 보낸다.

| 조회 | 가능? | 경로 |
|---|---|---|
| 인스턴스 + 기간 (최신순) | ✓ | AP-1 |
| 다이제스트별 샘플·추이 | ✓ | AP-3, AP-6 |
| 환경 + 실행시간 구간 + 시간 (최신순) | ✓ | AP-4 (`dur_bucket` 파티션) |
| 인스턴스-시간 롤업 | ✓ | AP-5 |
| **환경 전체 Top 다이제스트 (기간 임의)** | ✗ | **Athena.** 500 파티션 fan-out은 하지 않는다 |
| **다중 필터 조합 + 임의 정렬** | ✗ | Athena |
| **SQL 텍스트 검색** | ✗ | Athena ([OPEN-Q-08](OPEN-QUESTIONS.md)) |
| 계정별 워크로드 집계 | ✓ (전용 엔티티) | AP-16 |

"환경 전체 Top 다이제스트"는 UI에서 자주 쓰일 화면이다. 그래서 **시간 단위로 미리 집계한
Top 목록을 별도 항목으로 만들어 둔다**(AP-17: `PK = TOP#<env>#<hour_bucket>`).
롤업 플러시 시점에 계산하므로 추가 조회 비용이 없다. 기간이 긴 조회(월간)는 Athena.

**핫/콜드 통합 페이지네이션** — 경계를 교차하는 조회는 커서에 두 저장소의 위치를 모두
담아야 한다. 커서 구조를 `{ddb: LastEvaluatedKey?, athena: {exec_id, next_token}?, phase}`로
정의하고, DynamoDB 구간을 먼저 소진한 뒤 Athena 구간으로 넘어간다(`phase` 전환).
→ [13 §1.1](13-api-spec.md)에 명시한다.

**재검토 조건** — GSI가 4개를 넘거나, 애드혹 조회 요구가 반복되면 Aurora PostgreSQL 재검토.

## ADR-004. 콜드 저장소: S3 Tables(Iceberg), 적재는 DynamoDB 증분 내보내기

**결정** — 31일 초과 데이터는 S3 Tables(관리형 Iceberg)에 1년 보관한다.
적재는 **DynamoDB PITR 증분 내보내기 → S3 raw → Athena `MERGE INTO`** 일 1회.
스트리밍(Firehose/Kinesis)과 이중 쓰기를 쓰지 않는다.

**검토한 대안**

| 대안 | 판단 |
|---|---|
| **S3 Tables + DDB 증분 내보내기** | 채택 |
| 플레인 S3 Parquet + Glue + 증분 내보내기 | 차선. 스토리지·보관만료(Lifecycle)가 더 싸고 단순하지만, 컴팩션 잡과 백필 시 파티션 재작성 잡을 직접 만들어야 한다 |
| S3 Tables + Firehose 이중 쓰기(초기 제안) | 기각. 두 저장소가 갈라질 수 있어 정합성 검증 배치가 필수가 된다. 아카이브 실시간성이 필요 없는데 그 비용을 내는 셈 |
| DynamoDB에 13개월 전부 보관 | 기각. 스토리지는 감당 가능하지만 월간 리포트의 애드혹 SQL 집계를 잃는다 |
| Redshift / EMR Spark | 기각. 연 220GB 규모에 상시 클러스터는 과잉. Athena로 충분 |

**근거**
1. **파생 구조가 이중 쓰기보다 옳다.** DynamoDB를 단일 진실 원천으로 두면 두 저장소가
   갈라질 구조적 여지가 없다. 정합성 검증 배치, Firehose 스트림, 변환 Lambda가 전부 사라진다.
   **단 이 주장은 실시간 수집 경로에 한정된다** — 31일 초과 슬로우로그 백필은 DynamoDB를
   거치지 않고 Iceberg에 직접 적재하는 예외 경로이며, 그 경로에만 적용되는 규칙을
   [05 §8.3](05-collector.md)에 별도로 정의했다(F12).
2. 아카이브 신선도는 요구사항이 아니다. 31일 이내는 DynamoDB가 담당하므로 하루 지연이 무해하다.
3. Iceberg를 선택한 이유는 **`MERGE INTO`** 다. 잡 재시도가 멱등해지므로 실패 복구가
   "다시 돌리면 됨"으로 끝난다. 플레인 Parquet면 파티션 재작성 잡을 만들어야 한다.
4. 관리형 컴팩션 — 쓰기가 정시 버스트 패턴이라 파일 레이아웃이 균일하지 않다. 이걸 직접
   관리하고 싶지 않다.
5. 스키마 진화가 확실히 발생한다(지표 필드 추가). Iceberg는 이걸 정식 지원한다.

**대가**
- 증분 내보내기 포맷은 **`Item`이 아니라 `Keys`/`NewImage`/`OldImage`** 다(전체 내보내기와 다르다).
  언네스팅 SQL을 1회 작성해야 하고, 데이터 파일이 실행별 폴더가 아니라 공유 폴더에 누적되므로
  **매니페스트를 읽어 이번 실행 파일만 골라내야 한다** → [04 §4.3](04-data-model.md).
- **내보내기 창은 최소 15분 / 최대 24시간이다.** "실패 시 다음 주기가 누락 구간을 포함해
  재시도"는 1회 실패 후 48시간 창을 요구해 **API가 거부한다**.
  → 체크포인트~현재를 **24시간 미만 청크로 쪼개 순차 실행**한다(멱등이므로 안전).
  누락이 3일을 넘으면 알림 + 전체 내보내기 폴백.
- **변경 압축**: 같은 창 안에서 생성 후 삭제된 항목은 출력에 나타나지 않는다.
  슬로우 쿼리 레코드는 TTL(35일) 전에 삭제되지 않으므로 실무상 문제없지만,
  `_other` 롤업 재계산처럼 하루 안에 쓰고 지우는 데이터를 만들면 아카이브에서 사라진다.
  → **하루 안에 삭제되는 데이터를 만들지 않는다**는 제약으로 명시한다.
- 트랜잭션 경계가 보존되지 않는다(우리는 트랜잭션을 쓰지 않으므로 무관).
- PITR을 켜야 한다(스토리지 비용 증가. 단 복구 수단으로도 가치 있음).
- S3 Tables는 신규 서비스라 리전 가용성을 확인해야 하고 탈출구가 적다.
  → 완화: Iceberg 표준 포맷이므로 최악의 경우 일반 S3 Iceberg 테이블로 이관 가능.
- 컴팩션 요금이 별도 발생한다(규모상 월 몇 달러 수준, [16-cost.md](16-cost.md)).

**재검토 조건** — 배포 리전에 S3 Tables가 없거나, 볼륨이 연 10TB를 넘어 컴팩션 요금이
유의미해지면 플레인 S3 + 자체 컴팩션으로 전환.

## ADR-005. 슬로우 쿼리 캡처: 경량 탐지 + 타깃 심층 조회

> **M1 실측 반영 (2026-08-20)** — 전제가 **부분적으로만** 맞았다.
> `information_schema.PROCESSLIST.INFO` 는 `LONGTEXT` 가 아니라 `varchar(21845)` 이고
> **65,535바이트에서 절단**된다. 1,024 → 65,535 는 64배 개선이므로 이 결정은 유효하지만,
> "절단되지 않는다"는 서술은 틀렸다. 65KB 초과 SQL 은 `sql_text_truncated=true` 로 표시한다.
> 조회 비용 우려도 해소됐다 — 타깃 조회가 PS 폴링보다 오히려 싸다(0.8~0.9배, 스레드 88개).
> → [19 §A](19-m1-findings.md), [19 §F](19-m1-findings.md)

**결정** — 3단 구조.
1. **탐지**: `performance_schema.processlist`를 1초 주기로 조회 (경량, 뮤텍스 없음)
2. **심층**: 임계값 초과 스레드에 대해서만
   - `information_schema.PROCESSLIST WHERE ID = ?` → **절단되지 않은 전문 SQL**
   - `performance_schema.events_statements_current` → `DIGEST`, `ROWS_EXAMINED` 등 정확 지표
3. **플랜**: `EXPLAIN FORMAT=JSON FOR CONNECTION <id>` (ADR-006)

**맥락** — 1세대는 `performance_schema.processlist`만 읽었고, 이 뷰의 `INFO`는
`performance_schema.threads.PROCESSLIST_INFO`(VARCHAR(1024))에서 오므로 **1024바이트에서
잘린다.** README에는 `information_schema.PROCESSLIST`를 쓴다고 적혀 있었지만 코드는 그렇지
않았다. 긴 SQL이 조용히 손실되고 있었다.

**검토한 대안**

| 대안 | SQL 전문 | 부하 | 판단 |
|---|---|---|---|
| `performance_schema.processlist` 단독 | ✗ 1024B 절단 | 최저 | 기각(1세대 문제) |
| `information_schema.PROCESSLIST` 단독 1Hz | ✓ | 스레드 목록 뮤텍스 획득, 스레드 수천 개면 무시 못 함 | 기각 |
| **PS 탐지 + IS 타깃 조회 (하이브리드)** | ✓ | 정상 상태에서 tick당 쿼리 1건 | **채택** |
| `performance_schema_max_sql_text_length` 상향(파라미터 그룹) + `events_statements_current` | ✓ | 최저 | 보조 최적화. read-only 변수여서 **재시작 필요** → 기본 경로로 삼을 수 없다 |
| RDS 슬로우로그(CloudWatch) 단독 | ✓ + 정확 지표 | 대상 DB 부하 0 | 보완재로 채택([ADR-011](#adr-011-3중-소스를-app_digest로-조인한다)). 단 **실행 중** 캡처와 플랜 수집이 불가 |

**근거** — 정상 상태(느린 쿼리 없음)에서 tick당 쿼리 1건만 나간다. 비싼 조회는 실제로 문제가
있을 때만 발생한다. 이게 "대상 DB에 부하를 주지 않는다"는 주장의 근거다.

**대가**
- 탐지와 심층 조회 사이에 시차(수 ms)가 있어, 그 사이 쿼리가 끝나면 심층 정보를 못 얻는다.
  → 전문 SQL 없이 절단된 텍스트만 저장하고 `sql_text_truncated=true`로 표시.
- 조회 소스가 2개라 코드가 조금 복잡하다.
- **`information_schema.PROCESSLIST`는 `WHERE ID = ?` 조건이 있어도 내부적으로 전체 스레드
  목록을 채운 뒤 필터링할 가능성이 크다**(임시 테이블 기반 구현). 즉 "타깃 조회라서 싸다"는
  전제가 틀릴 수 있다. 슬로우 쿼리가 있을 때만 실행되므로 빈도는 낮지만, 스레드가 수천 개인
  인스턴스에서 폭주 시 부담이 된다. → [OPEN-Q-07](OPEN-QUESTIONS.md)에서 실측 확인하고,
  비용이 크면 심층 조회를 **후보 전체에 대해 1회**만 실행하도록 배치한다(이미 `ID IN (...)`
  형태이므로 코드 변경 없음).
- `TIME`은 "현재 상태에 머문 시간"이라 상태 전이가 있으면 실제 총 실행시간보다 짧을 수 있다.
  → `events_statements_current.TIMER_WAIT`가 있으면 그걸 우선한다.

**⚠ 자기 쿼리 식별을 주석으로 할 수 없다** — 초기 설계에서 `/* dbmon:<purpose> */` 주석으로
대상 DB의 다이제스트 통계에서 우리 쿼리를 골라내려 했다. **MySQL 다이제스트 정규화는 주석을
제거하므로 `DIGEST_TEXT LIKE '/* dbmon:%'`는 절대 매치되지 않는다.**
→ 자기 식별은 **모니터링 계정 이름**으로 한다:
- 우리 쿼리 제외: `USER NOT IN ('dbmon', ...)` (탐지 쿼리에 이미 있음)
- 우리 부하 계측: `sys.user_summary_by_statement_type WHERE user = 'dbmon'` 또는
  `events_statements_summary_by_account_by_event_name WHERE USER = 'dbmon'`
  → 계정 단위 집계는 다이제스트 정규화의 영향을 받지 않는다.
- 주석은 `SHOW PROCESSLIST`·슬로우로그·감사 로그에서 사람이 읽는 용도로만 유지한다
  (그 경로에서는 주석이 살아 있다).

**재검토 조건** — 파라미터 그룹 변경 + 재시작이 조직적으로 가능해지면
`performance_schema_max_sql_text_length=8192` + `events_statements_current` 단일 경로로
단순화할 수 있다(그때는 IS.PROCESSLIST 조회를 뺀다).

## ADR-006. 실행계획: 탐지 시점 `EXPLAIN FOR CONNECTION` (기회적 옵티마이저 플랜)

> **⚠ M1 실측으로 이 결정이 깨졌다 (2026-08-20)** — `EXPLAIN ... FOR CONNECTION` 은
> 타인 커넥션에 대해 **정적 전역 권한 전체**를 요구한다. `PROCESS` 도 `SUPER` 도 부족하고,
> RDS 는 마스터 유저에게도 `SUPER`·`FILE`·`SHUTDOWN` 을 주지 않으므로 **RDS·Aurora 에서는
> 어떤 계정으로도 불가능하다.** MySQL 버그 [#95850](https://bugs.mysql.com/bug.php?id=95850)
> 참조.
>
> **대체 결정**: `plan_source` 우선순위를 `none < rerun_as_select < rerun < for_connection`
> 으로 두고, RDS 에서는 `rerun`(원문 `EXPLAIN` 재실행, `SELECT` 권한만 필요)을 기본으로 한다.
> DML 은 `EXPLAIN UPDATE` 가 DML 권한을 요구하므로(`ERROR 1142`) 조건절을 `SELECT` 로 바꿔
> **근사 플랜**을 얻는다(`rerun_as_select`, UI 에 "근사" 배지).
> `for_connection` 은 자체 관리 MySQL 에서만 쓴다.
>
> 잃는 것: "실행 중 실제 플랜"은 RDS 에서 얻을 수 없다. DML 플랜은 1세대(없음)보다는
> 낫지만 정확하지 않다. → [19 §B](19-m1-findings.md)

**결정** — 슬로우 쿼리를 탐지한 즉시, 별도 연결에서
`EXPLAIN FORMAT=JSON FOR CONNECTION <processlist_id>`를 실행한다.
실패 시에만 SELECT에 한해 사후 `EXPLAIN` 재실행으로 폴백한다.

**용어를 정확히 쓴다** — 이것은 **실행 결과가 아니라 옵티마이저가 선택한 플랜**이다.
실제 처리 행수·단계별 소요 시간은 들어 있지 않다(그건 `EXPLAIN ANALYZE`인데 재실행이 필요하다).
UI와 문서에서 "실제 실행 플랜"이라고 쓰지 않고 **"실행 중 캡처한 옵티마이저 플랜"**으로
표기한다. 과장은 오진을 만든다.

**맥락** — 1세대는 쿼리가 끝난 뒤 SQL을 다시 `EXPLAIN`했다. 문제:
- 통계·데이터가 변해서 **당시 플랜과 다를 수 있다**
- UPDATE/DELETE는 아예 수집을 포기했다
- 프로시저 내부 `SELECT ... INTO`도 포기

**근거**
1. 실제로 실행 중인 플랜을 그대로 얻는다. "왜 느렸나"에 답하려면 당시 플랜이어야 한다.
2. DML도 커버된다. 재실행이 아니라 기존 플랜을 읽는 것이므로 부수효과가 없다.
3. 재실행 방식은 대상 DB에 실제 쿼리를 한 번 더 던지는 것과 다름없다(EXPLAIN도 최적화 단계를
   수행). in-flight는 그 비용이 없다.

**대가**
- **레이스**: 쿼리가 이미 끝났으면 실패한다. 임계값(기본 2초)을 넘긴 쿼리 대상이라 성공률은
  높지만 100%는 아니다. → NFR-P-04에서 80% 이상을 목표로 두고 실측한다.
- 일부 문장은 EXPLAIN 불가하다(프로시저 호출, SET, DDL). → 에러 코드를 `plan_error`에 기록.
- **Prepared statement / 서버 사이드 prepare 경로에서 동작하지 않을 수 있다.**
  ORM이 prepared statement를 쓰는 애플리케이션이 많으므로 성공률에 직접 영향을 준다.
  → M1-2 스파이크에서 prepared statement 케이스를 반드시 포함해 측정한다.
- **사후 재실행 플랜은 원래 플랜이 아니다.** 바인드 값, 세션 변수, 트랜잭션 스냅샷,
  임시 테이블 상태가 모두 다르다. `plan_source=rerun`을 UI에서 명확히 구분하고
  "당시 플랜과 다를 수 있음" 경고를 항상 표시한다. 어드바이저는 `rerun` 플랜에 대해
  confidence를 한 단계 낮춘다.
- `EXPLAIN FORMAT=TREE FOR CONNECTION` 지원 여부를 버전별로 확인해야 한다.
  → [OPEN-Q-05](OPEN-QUESTIONS.md). 미지원이면 JSON만 수집하고 TREE는 폴백 경로에서만.
- 별도 연결이 필요하므로 인스턴스당 연결 1개를 추가로 쓴다.

**부수 효과(이득)** — in-flight 경로는 대상 테이블에 대한 `SELECT` 권한을 요구하지 않을
가능성이 있다(플랜을 재수립하지 않으므로). 사실이면 모니터링 계정 권한을 크게 줄일 수 있다.
→ [OPEN-Q-06](OPEN-QUESTIONS.md)에서 검증. 검증 전까지는 `SELECT` 권한을 요구하는 전제로 설계.

## ADR-007. 모니터링 DB 계정: IAM DB Auth (비밀번호 없음)

**결정** — 모니터링 계정을 `IDENTIFIED WITH AWSAuthenticationPlugin AS 'RDS'`로 만들고,
연결 시마다 `rds:generate-db-auth-token`으로 15분 유효 토큰을 발급받아 TLS로 접속한다.
비밀번호 방식은 IAM Auth를 쓸 수 없는 인스턴스에 대한 폴백으로만 둔다.

**맥락** — 1세대는 `MGMT_USER_PASS`가 환경변수/Secrets Manager에 상주했다. 대상 DB 전체에
같은 비밀번호를 쓰는 구조라 유출 영향 범위가 전체였다.

**근거**
1. **상시 존재하는 자격증명이 없다.** 유출할 대상이 없다.
2. 접근 권한이 IAM 정책으로 표현되므로 감사·회수가 IAM에서 끝난다.
3. TLS가 강제된다(IAM Auth는 SSL 필수).
4. 로테이션이라는 개념 자체가 사라진다.

**대가**
- 인스턴스에서 IAM DB Auth를 활성화해야 한다 → **프로덕션 RDS 변경 작업**.
  → FR-CRD-09: prd 대상은 별도 2차 확인 + 감사 로그.
- **IAM 인증은 DB 인스턴스 측 메모리를 추가로 사용한다.** AWS 안내에 따르면 수백 MiB
  수준의 여유를 확보하라고 되어 있다. `db.t3.micro`·`db.t4g.small` 같은 작은 인스턴스에서
  이건 무시할 양이 아니고, **관측 도구가 관측 대상의 가용 메모리를 잠식하는** 상황이 된다.
  → 부트스트랩 계획 단계에서 인스턴스 클래스와 `FreeableMemory`를 확인하고,
  메모리 여유가 임계 미만이면 **비밀번호 방식을 권고**한다. 인스턴스 클래스별 정책을
  설정으로 둔다(예: `db.t*` 계열은 기본 비밀번호 방식).
  → [OPEN-Q-17](OPEN-QUESTIONS.md)에서 실제 메모리 증가량을 계측한다.
- 신규 연결 초당 약 200개 제한 → 연결 풀을 유지해야 하고, 풀 전체 재생성이 폭주하지 않도록
  지터를 넣어야 한다.
- IAM 정책 리소스가 `dbi-resource-id` 기반이라, 인스턴스 교체 시 리소스 ID가 바뀌면 정책을
  갱신해야 한다. → 와일드카드(`dbuser:*/dbmon`)로 두고 근거를 문서화(NFR-S-09).
- 토큰 발급이 리전별 서명이므로 크로스 리전 대상은 대상 리전 기준으로 서명해야 한다.

**재검토 조건** — IAM Auth 연결 제한이 실제 병목이 되면(연결 폭주 시나리오),
해당 인스턴스만 Secrets Manager 비밀번호 + 로테이션으로 전환.

## ADR-008. 마스터 자격증명: 3소스 지원, 저장하지 않음

**결정** — 부트스트랩 전용으로 3가지 소스를 지원한다.
1. RDS 관리형 마스터 시크릿 (`DescribeDBInstances`의 `MasterUserSecret.SecretArn`) — **우선**
2. 사용자가 지정한 Secrets Manager 시크릿 ARN
3. UI 1회 수동 입력 — 메모리에만, `zeroize`로 폐기

**기본 경로는 (0) 수동 SQL 실행이다** — 위 3소스 앞에 0번을 둔다.

```
0. 앱이 실행할 SQL과 CLI 명령을 생성해 보여주고, DBA가 직접 실행한다.
   앱은 그 결과를 검증만 한다 (권한 diff 조회).
```

**왜 이걸 기본값으로 하는가** — 자동 부트스트랩은 앱의 신뢰 경계를 크게 넓힌다.
`zeroize`는 **우리가 소유한 버퍼 하나**를 지울 뿐이고, HTTP 본문 버퍼·serde 중간 문자열·
할당자 재사용 영역·패닉 백트레이스·관측 계층의 복사본까지 지웠음을 **증명할 수 없다**
(T-30). WAF가 요청 본문을 검사하다 규칙에 걸리면 WAF 로그에도 남을 수 있다.

반면 수동 경로는 그 위험이 0이고, DBA가 실행하는 SQL은 어차피 우리가 생성한 것과 같다.
잃는 것은 편의뿐이다. **500대를 일괄 부트스트랩해야 하는 조직에서만 자동 경로가 의미 있다.**

| 경로 | 기본 | 필요 조건 |
|---|---|---|
| (0) 수동 SQL 실행 | **✓ 기본** | 없음. `dbmon-bootstrap` IAM 정책 미부여 |
| (1) RDS 관리형 시크릿 | 옵션 | 관리형 마스터 시크릿 활성 + `secretsmanager:GetSecretValue` on `rds!*` |
| (2) 지정 시크릿 ARN | 옵션 | 태그 조건 만족하는 시크릿 |
| (3) UI 수동 입력 | **옵션(비권장)** | 위 셋이 모두 불가한 레거시 환경 |

**근거** — RDS 관리형 마스터 시크릿이 켜져 있으면 사람이 비밀번호를 만질 필요가 없다.
그게 (1)의 가치다. (3)은 최후 수단이며 UI에 위험을 명시한다.

**멱등성 주의** — `CREATE USER IF NOT EXISTS`는 **잘못된 기존 상태를 교정하지 않는다.**
계정이 이미 있으면 인증 플러그인·`REQUIRE SSL`·초과 권한이 어떻든 조용히 통과한다.
이건 계정 선점 공격(T-28)의 통로다.
→ 존재하는 계정에 대해서는 `SHOW CREATE USER`로 플러그인과 SSL 요구를 확인하고,
**기대와 다르면 GRANT를 실행하지 않고 중단**한다(제안이 아니라 차단).

**대가** — 4경로를 구현·테스트해야 한다. 기본 경로가 수동이므로 설치 가이드가 길어진다.

**재검토 조건** — 관리형 시크릿 커버리지가 100%가 되면 (2)(3)을 제거.

## ADR-009. 시계열 저장소를 도입하지 않는다

**결정** — 실시간 지표(5초 해상도 `global_status` 델타)는 **워커 메모리 링버퍼**에만 둔다.
장기 추세는 CloudWatch가 담당한다. Prometheus/Timestream/InfluxDB를 도입하지 않는다.

**근거**
- 500대 × 5초 × 20지표 = 초당 2000포인트. 이걸 영속화하면 시계열 스토어 운영이 새로 생긴다.
- 실시간 패널의 용도는 "지금 이 인스턴스가 어떤 상태인가"이고, 최근 60분이면 충분하다.
- 장기 추세는 CloudWatch에 이미 있다. 같은 걸 두 번 저장할 이유가 없다.
- 링버퍼 메모리: 500대 × 720포인트 × 20지표 × 8바이트 ≈ 58MB. 무시 가능.

**⚠ EMF도 공짜가 아니다** — "EMF로 `PutMetricData` 비용을 피한다"는 API 호출료만 피한다는
뜻이다. **EMF가 생성한 메트릭은 커스텀 메트릭으로 메트릭당 월 $0.30 과금된다.**

차원에 `instance_id`를 넣으면 고유 메트릭 수가 인스턴스 수에 비례한다:
```
CollectTickDuration(instance_id)             500
CollectFailures(instance_id, reason 6종)     500 × 6 = 3,000
TargetDbQueryDuration(instance_id, 용도 6종) 500 × 6 = 3,000
SlowQueriesCaptured(instance_id)             500
CollectStaleness(instance_id)                500
DigestRollupItems(instance_id)               500
                                           ─────────
                                             8,000개 × $0.30 = 월 $2,400
```
[06 §2.3](06-discovery-metrics.md)에서 설계로 제거한 CloudWatch $3,240 문제를
자체 관측성으로 되살리는 셈이다.

**대응 — 차원에서 `instance_id`를 뺀다.**

| 계층 | 방식 | 고유 메트릭 수 |
|---|---|---|
| 플릿 집계 메트릭 | `CollectFailures(reason)`, `CollectTickDuration`(차원 없음, 통계 분포) 등 | **108개** = 월 $32 |
| 인스턴스별 값 | **구조화 로그 필드**로만 남긴다. 조회는 Logs Insights / CloudWatch Contributor Insights | $0 |
| 인스턴스별 알람이 필요한 소수 | "watched" 화이트리스트 20대만 메트릭화 | 20 × 6 = 120개 = 월 $36 |
| **합계** | | **228개 = 월 $69** (절감 약 $2,331) |

항목별 정확한 카디널리티는 [14 §5.2](14-infrastructure.md)의 표에 있다. 이 문서와 그 표,
[16 §2.3](16-cost.md)의 값은 항상 일치해야 한다.

인스턴스별 알람은 대부분 불필요하다. "어느 인스턴스가 실패했나"는 알림 본문에 담으면 되고
(알림 평가는 앱이 하므로 CloudWatch 메트릭이 필요 없다), CloudWatch 알람은 **플릿 수준의
이상**(실패율 급증, 전체 지연)만 감시하면 된다.

**대가**
- 인스턴스별 CloudWatch 대시보드를 만들 수 없다. → 우리 UI가 그 역할을 한다.
- Logs Insights 조회는 CloudWatch 메트릭보다 느리고 스캔 과금이 있다. 조사용이므로 수용.
- 워커 재시작 시 실시간 그래프가 비워진다(60분 후 복원). 수용.
- CloudWatch에 없는 자체 지표(예: `Innodb_row_lock_waits` 델타)의 장기 추세를 볼 수 없다.
  → 정말 필요한 것만 시간 롤업으로 DynamoDB에 넣는다(다이제스트 롤업과 같은 방식).
- 워커가 여러 대면 특정 인스턴스의 실시간 데이터가 특정 워커에만 있다.
  → API 역할과 collector 역할이 분리되는 2단계에서 문제가 된다. [OPEN-Q-04](OPEN-QUESTIONS.md)

## ADR-010. 다이제스트는 시간 롤업 + 상위 N으로 영속화한다

**결정** — 다이제스트 델타는 60초마다 계산하되, **영속화는 시간 단위**로 한다.
인스턴스-시간별로 **총 실행시간 상위 N개(기본 200)를 hard cap으로 저장**하고, 나머지는
`_other` 1행으로 합산한다. 1분 해상도는 메모리 링버퍼(최근 60분)에만.

**`상위 N` 은 hard cap이다. `OR 임계값` 이 아니다.**
초기 설계는 "상위 200개 **또는** 총 실행시간 100ms 이상"이었는데, `OR`는 상한이 아니다
— 100ms를 넘는 다이제스트가 수천 개면 수천 행이 저장된다. 비용 통제 장치가 통제하지 못한다.
→ 규칙을 뒤집는다: **먼저 임계값(100ms)으로 걸러 후보를 만들고, 그 안에서 상위 N개만** 저장.
`N`이 절대 상한이다. 잘려나간 후보 수를 `truncated_candidates`로 기록해 N이 부족한지 관측한다.

**맥락** — 1분 해상도를 그대로 적재하면 500대 × 1440분 × 활성 다이제스트 300개 ≈
**일 2억 행**. DynamoDB 쓰기만 하루 수백 달러, Athena 스캔량도 감당 불가.

**근거**
- 시간 롤업 + 상위 200 → **일 241만 행 ≈ 720MB**(항목 300B 기준). 100배 이상 축소.
- 성능 분석에서 의미 있는 건 상위 다이제스트다. 롱테일 개별 항목을 1분 해상도로 1년 보관할
  이유가 없다.
- `_other` 합산 행을 남기면 "관측된 다이제스트가 전체 실행시간의 몇 %를 설명하는가"를 항상
  계산할 수 있다. 이게 없으면 상위 N 제한이 통계를 왜곡한다.

**시간창 백분위수는 누적 `QUANTILE_95`에서 얻을 수 없다** — 이건 별개의 오류였다.
`events_statements_summary_by_digest.QUANTILE_95/99`는 **서버 시작 이후 누적 히스토그램에서
유도된 현재 추정값**이다. 두 스냅샷의 차를 구해도 "이 시간창의 P95"가 나오지 않는다.
누적 `MIN_TIMER_WAIT` / `MAX_TIMER_WAIT`도 같다.

→ 시간창 백분위수가 필요하면 **`performance_schema.events_statements_histogram_by_digest`의
버킷 카운트 델타**를 써야 한다. 이 테이블은 다이제스트별로 지연 버킷(bucket_number,
bucket_timer_low/high, count_bucket)을 누적하므로, 버킷 카운트를 차분하면 그 창의 분포가 나온다.

| 지표 | 시간창 값을 얻는 방법 |
|---|---|
| 실행 횟수, 총 시간, rows_* 합계 | `SUM_`/`COUNT_` 컬럼 델타 ✓ |
| 창 내 평균 | `델타 total / 델타 count` ✓ |
| 창 내 P95 / P99 | **히스토그램 버킷 델타** (별도 쿼리) |
| 창 내 최대 | 히스토그램의 최상위 비어있지 않은 버킷 상한 (근사) |
| 전체 기간 최대 | `MAX_TIMER_WAIT` — 라벨을 "누적 최대"로 명확히 |

**비용 판단** — 히스토그램 테이블은 다이제스트당 버킷 450개 × 활성 다이제스트 수라
페이로드가 크다. 그래서:
- 기본은 **히스토그램을 수집하지 않는다.** 시간 롤업에는 평균과 누적 최대만 담고,
  라벨을 정확히 붙인다("P95(누적 추정)", "최대(누적)").
- 특정 다이제스트의 정확한 시간창 분포가 필요할 때만(어드바이저 실행, 개선 리포트)
  **해당 다이제스트에 한정해** 히스토그램을 조회한다(`WHERE DIGEST = ?`).
- 리포트에서 "P95"를 쓸 때는 무엇의 P95인지 명시한다. 개선 리포트의 before/after 비교는
  히스토그램 기반으로 정확히 계산한다(대상 다이제스트 1개이므로 비용이 없다).

**대가**
- 시간 경계 안에서의 분포를 잃는다(예: 정시 5분간의 스파이크). → 실시간 링버퍼와 슬로우 쿼리
  개별 레코드가 그 구간을 커버한다.
- 롤업의 "P95"는 시간창 값이 아니다. 라벨링을 틀리면 리포트가 거짓말을 한다.
  → 컬럼명을 `p95_ms_cumulative_snapshot`으로 길게 두어 오용을 막는다.
- 롱테일 다이제스트는 개별 추적이 안 된다. → 임계값을 낮추면 커버되지만 볼륨이 늘어난다.
  FR-DGS-01c에서 볼륨 영향을 UI에 추정 표시한다.
- 정시에 쓰기 버스트가 발생한다. → 인스턴스별로 플러시 시각에 지터(0~60초)를 준다.
- 워커 재시작 시 해당 시간의 부분 데이터가 유실된다. → `partial=true` 플래그로 표시해
  집계·리포트에서 구분한다.

**재검토 조건** — 상위 200이 실제 워크로드의 95%를 설명하지 못하면 N을 올린다(측정 후 조정).

## ADR-011. 3중 소스를 `app_digest`로 조인한다

> **M1 실측 확인 (2026-08-20)** — `max_digest_length` 가 다른 인스턴스 사이에서 같은 쿼리의
> `DIGEST` 해시가 **달라진다**(1024 → `61416d95…`, 4096 → `033f75ac…`).
> `app_digest` 는 필수다. **결정 유지.**
> 단 정규화 규칙표는 실측으로 11건 정정했고([19 §C](19-m1-findings.md)),
> `app_digest` : `mysql_digest` 가 **1:N** 임이 드러났다([19 §D](19-m1-findings.md)).

**결정** — 캡처 소스 3개를 모두 쓰고, **자체 정규화 해시 `app_digest`** 를 공통 조인 키로 삼는다.
`mysql_digest`는 인스턴스별 메타데이터로 함께 저장한다.

| 소스 | 커버리지 | SQL 텍스트 | 플랜 | 지표 정확도 |
|---|---|---|---|---|
| `information_schema.PROCESSLIST` 1Hz | 1초 이상 **실행 중** 쿼리 | 전문(리터럴) | in-flight | 근사(초 단위) |
| `events_statements_summary_by_digest` | **전체 워크로드 100%** | 정규화 `DIGEST_TEXT` + `QUERY_SAMPLE_TEXT` | 없음 | 정확(피코초) |
| CloudWatch 슬로우로그 | `long_query_time` 초과 **완료** 쿼리 | 전문(리터럴) | 없음 | 정확(rows_examined 등) |

**근거**
- 각 소스의 사각지대가 서로 다르다. 폴링은 sub-second를 못 보고, 다이제스트는 개별 실행과
  플랜을 못 주고, 슬로우로그는 실행 중을 못 잡는다. 셋을 합치면 사각지대가 없다.
- **`mysql_digest`를 공통 키로 쓸 수 없는 이유**: 다이제스트는
  `performance_schema_max_digest_length`에 따라 절단되므로, 파라미터 그룹이 다른 인스턴스
  사이에서는 긴 쿼리의 다이제스트가 달라진다. 또 CloudWatch 슬로우로그에는 다이제스트가 아예
  없다. 크로스 인스턴스 그룹핑을 하려면 자체 해시가 필요하다.
- `app_digest`는 이 요구사항의 핵심이기도 하다: "실시간 캡처한 실제 쿼리"와 "바인드 변수화된
  그룹 쿼리"를 묶어서, 그룹 통계 + 실행 가능한 실제 샘플을 함께 보여주는 것.

**역할 분담을 정확히 한다** — 자체 정규화가 서버 다이제스트를 대체하는 것이 아니다.

| 용도 | 권위 있는 값 |
|---|---|
| **인스턴스 내** 그룹핑·조인 | **서버 `DIGEST`** (`mysql_digest`). 우리가 계산하지 않는다 |
| **크로스 인스턴스** 그룹핑 | `app_digest` (파라미터 그룹 차이로 서버 다이제스트가 갈릴 수 있으므로) |
| 슬로우로그 레코드에 다이제스트 부여 | **`STATEMENT_DIGEST(sql)`** 서버 함수 (아래 참조) |
| 텍스트 검색·표시 | `digest_text` |

**`STATEMENT_DIGEST()` 를 활용한다** — MySQL 8.0에는 임의 SQL의 다이제스트 해시를 계산하는
`STATEMENT_DIGEST(statement)`와 정규화 텍스트를 반환하는 `STATEMENT_DIGEST_TEXT(statement)`
함수가 있다. 슬로우로그에서 파싱한 SQL에 대해 이 함수를 호출하면 **서버가 계산한 것과 동일한
다이제스트**를 얻는다. 자체 lexer로 에뮬레이션할 필요가 없다.

```sql
/* dbmon:stmtdigest */
SELECT STATEMENT_DIGEST(?) AS digest, STATEMENT_DIGEST_TEXT(?) AS digest_text
```
- 대상 DB에 쿼리 1건이 추가되지만, 슬로우로그 백필 시에만 발생하고 배치로 묶을 수 있다.
- 함수 결과는 **호출하는 서버의 `max_digest_length`·`sql_mode`·문자셋**에 영향받는다.
  같은 인스턴스에 대해 호출하면 그 인스턴스의 다이제스트와 일치한다.
- 이 함수를 쓸 수 없거나(대상 DB 도달 불가한 백필) 크로스 인스턴스 그룹핑이 필요한 경우에만
  자체 `app_digest`를 쓴다.

**대가**
- 자체 정규화의 **수렴 정합성**을 보장해야 한다:
  `app_digest(raw_sql)` == `app_digest(digest_text(raw_sql))`.
  `IN (1,2,3)` → MySQL은 `IN (...)`으로 축약하므로 우리도 같게 해야 한다.
  → [05 §3](05-collector.md)에 규칙을 명시하고 골든 코퍼스로 강제한다.
  **자체 lexer는 `sql_mode`·문자셋·버전별 문법에서 서버와 어긋날 수밖에 없다.** 그래서
  자체 정규화의 역할을 "크로스 인스턴스 그룹핑 키"와 "마스킹"으로 **제한**하고,
  정확한 다이제스트가 필요한 곳에는 서버 값을 쓴다.
- 정규화 규칙 변경은 과거 데이터의 `app_digest`를 무효화한다. → `digest_algo_version`을
  **슬로우 쿼리·롤업·아카이브 롤업 전부**에 저장한다(F29. 초기 설계는 슬로우 쿼리에만 있었다).

  **버전 전환 절차** — "버전이 다르면 경고"만으로는 부족하다. 규칙을 바꾸면
  (a) [12 §2.2](12-reporting.md)의 "직전 6개월 미관측 = 신규" 쿼리가 **전 워크로드를 신규로
  판정**하고, (b) 개선 리포트의 before/after가 끊기고, (c) `digest_texts`에 구·신 행이
  공존하지만 둘을 잇는 매핑이 없다.

  ```
  1. 전환 기간(2주)을 선언한다
  2. 그 기간에는 두 해시를 동시 산출해 저장 (app_digest_v2 속성 추가)
  3. (old_digest → new_digest) 매핑 테이블을 생성
       PK = DGMAP#<old_algo_version>   SK = <old_digest>
  4. 전환 종료 후 app_digest 를 v2 로 승격, 매핑 테이블은 400일 보관
  5. 리포트 쿼리는 버전 경계를 명시적으로 표시하고, 경계를 넘는 비교는
     매핑 테이블로 조인한다
  ```

  전환 비용이 크므로 **정규화 규칙 변경은 골든 코퍼스 테스트 실패를 고칠 때만** 한다.
- **`DIGEST_TEXT` 절단과 `DIGEST` 해시의 관계는 확정되지 않았다.** 절단이 해시까지 바꾸는지
  (토큰 스트림이 잘려서) 아니면 텍스트만 잘리는지 실측이 필요하다.
  → [OPEN-Q-16](OPEN-QUESTIONS.md). 해시가 바뀌지 않는다면 `mysql_digest`를 크로스 인스턴스
  키로도 쓸 수 있어 `app_digest`의 역할이 더 줄어든다.

## ADR-012. 인증: Cognito + 앱 레벨 OIDC (PKCE)

**결정** — Cognito User Pool + Managed Login. SPA는 Authorization Code + PKCE(퍼블릭 클라이언트,
시크릿 없음). 백엔드는 JWKS로 JWT를 검증한다. 인가는 `cognito:groups` 기반 RBAC.

**검토한 대안**

| 대안 | 판단 |
|---|---|
| **앱 레벨 OIDC(PKCE) + 백엔드 JWT 검증** | 채택 |
| ALB `authenticate-cognito` 액션 | 기각. 앱 코드가 줄어드는 건 매력적이지만, SPA의 XHR/WS 요청이 401에서 IdP로 **리다이렉트**되면 `fetch`가 그걸 따라가며 CORS/파싱 오류를 낸다. WebSocket 업그레이드와도 궁합이 나쁘다 |
| 자체 IdP(Keycloak 등) | 기각. 운영 대상 추가 |
| IAM Identity Center 단독 | 기각. 외부 협력사·비 AWS 계정 사용자 수용이 어렵다 |

**근거** — ID/비밀번호와 SAML/OIDC 페더레이션을 한 User Pool에서 동시에 수용할 수 있고,
IdP 추가가 API 호출(`CreateIdentityProvider`)로 되므로 관리자 UI에서 다룰 수 있다(FR-AUT-04).

**공개(미인증) 엔드포인트 목록을 한 곳에 고정한다** — "「/healthz」만 공개"라고 썼지만
[13-api-spec.md](13-api-spec.md)는 `/readyz`, `/api/openapi.json`, `/api/auth/config`도
미인증으로 둔다. 계약을 하나로 통일한다.

| 엔드포인트 | 공개 이유 | 노출되는 정보 |
|---|---|---|
| `/healthz` | ALB·systemd 헬스체크 | 없음 (200 고정) |
| `/readyz` | ALB 대상 등록 판정 | 의존성 상태(있음/없음). **어떤 의존성인지는 노출하지 않는다** |
| `/api/auth/config` | SPA가 로그인 전에 필요 | 공개 OIDC 메타데이터(도메인·client_id·IdP 이름) |
| `/api/openapi.json` | 개발 편의 | API 구조. **프로덕션에서는 인증 필요로 전환한다** (설정) |

`/readyz`는 미인증이므로 의존성 호출을 유발한다(DoS 벡터). **결과를 5초 캐시**하고
WAF rate-based rule로 IP 단위 제한을 걸어 T-35와 같은 방식으로 방어한다.

**KMS 조건식 오류** — `kms:ViaService`에 `"dynamodb.*.amazonaws.com"` 같은 와일드카드 값을
쓰면서 `StringEquals`를 썼다. **와일드카드가 리터럴로 비교되어 절대 매치되지 않는다.**
`StringLike`로 고친다([§5.2](08-security-auth.md)).

**대가**
- 토큰 갱신, JWKS 캐시·회전, 로그아웃 처리를 직접 구현해야 한다.
- WebSocket 인증을 별도로 설계해야 한다(브라우저 `WebSocket`은 헤더를 못 붙임).
  → 연결 직후 첫 메시지로 토큰 전달 + 서버 검증 후 구독 허용. 쿼리스트링에 토큰을 넣지 않는다
  (ALB·CloudWatch 액세스 로그에 남는다).
- Cognito 장애 시 신규 로그인이 불가하다. 기존 토큰은 JWKS 캐시로 만료까지 동작.

## ADR-013. 프론트엔드: React + TS + Vite 유지, 차트는 용도별 이원화

**결정** — 기존 스택(React, TypeScript, Vite, Tailwind)을 유지하고 React 19로 올린다.
서버 상태는 TanStack Query, 밀집 테이블은 TanStack Table + Virtual.
**차트는 밀집 시계열에 uPlot(canvas), 단순 막대·파이에 Recharts.**

**근거**
- 기존 대시보드 자산(플랜 시각화, 다이제스트 테이블, 메트릭 차트)이 그대로 이식된다.
- Recharts는 SVG라 포인트가 수천 개를 넘으면 DOM 노드 수 때문에 프레임이 떨어진다. 실시간
  패널(5초 × 60분 = 720포인트 × 다중 시리즈)과 1개월 메트릭(1분 × 43200포인트)은 canvas가
  필요하다. uPlot은 이 용도의 표준 선택이고 번들이 ~50KB다.
- 차트 라이브러리를 2개 두는 대가는 있지만, 하나로 통일하려면 단순 차트까지 uPlot으로
  직접 그려야 해서 코드가 더 늘어난다.

**프레임워크 대안** — 사용자가 "프론트 언어 추천"을 물었으므로 근거를 남긴다.

| 대안 | 이 워크로드 적합성 | 판단 |
|---|---|---|
| **React 19 + TS (채택)** | 충분. 고빈도 렌더는 canvas 차트가 담당하고 React는 셸·표만 그린다 | 채택. **근거는 성능이 아니라 기존 자산 재사용**(1세대 대시보드 컴포넌트 이식) + 생태계(TanStack, shadcn/ui) |
| Svelte 5 (runes) / SolidJS | 세밀한 반응성으로 재렌더 비용이 낮다. 실시간 대시보드에 이론적 이점 있음 | 기각. 이점이 **canvas 차트를 쓰는 순간 대부분 사라진다**. 1세대 자산 이식 비용 + 팀 학습 비용이 이득을 넘는다 |
| Vue 3 | React와 대등 | 기각. 기존 자산이 React |
| 순수 TS + Web Components | 의존성 최소 | 기각. 표·필터·라우팅을 직접 만들어야 한다 |

**재검토 조건** — canvas 밖 영역(표, 필터, 실시간 목록)에서 INP 200ms를 못 맞추면
그 화면만 세밀 반응성 프레임워크로 분리하는 것을 검토한다. 전면 교체는 하지 않는다.

**차트는 uPlot 하나로 시작한다** — 초기 설계는 uPlot + Recharts 2개였다.
라이브러리 2개는 포맷팅·툴팁·테마·접근성·테스트를 두 벌 만드는 일이다.
문서에 등장하는 차트는 대부분 시계열이고, 나머지(막대·비율)는 **HTML/CSS로 그리는 편이
Recharts를 들이는 것보다 싸다**(높이 %를 가진 div, `<meter>`, 표).

→ M6에는 `<TimeSeriesChart>`(uPlot)와 HTML/CSS 기반 `<BarList>` / `<Sparkline>`만 만든다.
Recharts는 **"HTML/CSS로 만들기 어려운 구체적 차트가 실제로 필요해질 때"** 추가한다
(산점도, 트리맵 등). 그때도 컴포넌트 1개만 감싼다.

**대가** — 차트 컴포넌트 추상화 계층을 얇게라도 둬야 라이브러리 선택이 화면 코드에 새지 않는다.

## ADR-014. 실시간 전송: WebSocket

**결정** — 실시간 슬로우 쿼리 스트림과 실시간 지표 푸시는 WebSocket으로 한다.

**검토한 대안**
- **SSE(`EventSource`)**: 단방향이면 충분해 보이지만 브라우저 `EventSource`가 `Authorization`
  헤더를 붙일 수 없다. 우회하려면 토큰을 쿼리스트링에 넣거나(로그 유출) fetch 기반 SSE
  폴리필을 써야 한다. 또 구독 대상(인스턴스 선택)을 바꿀 때마다 재연결이 필요하다.
- **폴링(TanStack Query `refetchInterval`)**: 가장 단순. 실시간 지표는 5초 폴링으로도 된다.
  하지만 500대 구독 시 요청 수가 늘고, 슬로우 쿼리 발생 즉시 표시라는 요구(FR-UI-08)에
  지연이 생긴다.
- **WebSocket**: 채택. 양방향이라 구독 변경을 메시지로 처리할 수 있고, 토큰을 첫 메시지로
  안전하게 전달할 수 있다. 1세대에서 이미 운영 경험이 있다.

**⚠ 워커 2대 권장과 WS 팬아웃 미해결이 모순이었다** — [14 §6.2](14-infrastructure.md)는
무중단 배포를 위해 "1단계부터 워커 2대 유지"를 권하는데, 그러면 클라이언트가 붙은 노드와
해당 인스턴스를 수집하는 노드가 달라져 실시간 이벤트를 전달할 경로가 없다.
스티키 세션은 **클라이언트를 특정 노드에 고정**할 뿐 수집 소유권 문제를 해결하지 않는다.

**해결 — ADR-018의 1단계와 맞춘다.**
1단계에서는 **active collector가 1대**다(나머지는 standby). 따라서:
- ALB 대상 그룹에 **active 노드만** 등록한다. standby는 `/readyz`를 503으로 응답해
  자동으로 대상에서 빠진다.
- 클라이언트는 항상 active 노드에 붙으므로 팬아웃이 필요 없다. 스티키 세션도 불필요하다.
- 배포 시: 새 노드 기동 → 리더 리스 인수 → `/readyz` 200 → ALB 등록 → 구 노드 등록 해제.
  WS 클라이언트는 "재연결 요청" 메시지를 받고 새 노드로 붙는다. 중단은 수 초.
- **API 처리량이 1노드로 부족해지거나 샤딩이 필요해지면** 그때
  [OPEN-Q-04](OPEN-QUESTIONS.md)를 해소한다(Redis pub/sub 유력).

**MVP를 더 게으르게 갈 수도 있다** — 실시간 지표를 5초 HTTP 폴링 + `ETag`로 하면 WS 자체가
불필요하다. 그래도 WS를 택하는 이유는 (a) 슬로우 쿼리 발생 즉시 표시(FR-UI-08)가 폴링으로는
최대 5초 지연되고, (b) 구독 대상(인스턴스 선택)을 서버에 알려 대역폭을 줄일 수 있고,
(c) 1세대에서 이미 운영 경험이 있어서다.
→ M6 구현 시 WS가 복잡도를 감당할 만한지 재평가한다. 안 되면 폴링으로 내려간다.

**대가** — 재연결·백프레셔·하트비트를 직접 구현해야 한다. active 노드 1대 제약을 받는다.

## ADR-015. Athena 조회: 비동기 + 결과 캐시

**결정** — 콜드 티어 조회는 Athena 비동기 실행이다. API는 `execution_id`를 반환하고,
클라이언트는 폴링 또는 WebSocket 완료 통지로 결과를 받는다. 결과는 쿼리 지문 기준으로 캐시한다.

**근거** — Athena는 콜드 스타트 수 초 + 스캔에 비례한 시간이 걸린다. 동기 API로 감싸면
HTTP 타임아웃과 워커 스레드 점유가 생긴다.

**Athena가 이미 제공하는 것을 다시 만들지 않는다** — 초기 설계는 자체 잡 상태 머신 +
자체 결과 캐시 + WS 완료 통지를 두려 했다. Athena는 이미 다음을 제공한다:

| 필요한 것 | Athena 기능 |
|---|---|
| 실행 ID | `QueryExecutionId` |
| 상태 폴링 | `GetQueryExecution` (`QUEUED`/`RUNNING`/`SUCCEEDED`/`FAILED`/`CANCELLED`) |
| 결과 페이지네이션 | `GetQueryResults` + `NextToken` |
| 취소 | `StopQueryExecution` |
| 결과 캐시 | **워크그룹의 query result reuse** (동일 쿼리 재사용, 최대 재사용 기간 설정) |
| 스캔량·비용 | `Statistics.DataScannedInBytes` |

→ **자체 잡 테이블·자체 캐시를 만들지 않는다.**
`QueryExecutionId`를 그대로 클라이언트에 돌려주고(단 요청자 `sub`에 바인딩해 저장, T-17),
상태는 HTTP 폴링으로 조회한다. 결과 캐시는 **워크그룹 result reuse를 먼저 켜고**,
측정 후 부족하면 그때 애플리케이션 캐시를 추가한다.
WS 완료 통지도 만들지 않는다 — 폴링으로 충분하다(조회 1건에 사용자 1명).

**남는 것** — 단일 비행(single-flight)은 유지한다. 같은 쿼리를 동시에 요청한 여러 사용자가
각각 Athena 실행을 시작하면 워크그룹 스캔 한도(T-35)를 빨리 소진한다.
result reuse가 이걸 부분적으로 막지만 동시 시작은 막지 못한다.

**대가** — UI가 "실행 중" 상태를 다뤄야 한다.
→ 완화: TanStack Query 폴링으로 감싸 컴포넌트에서는 `isLoading`만 보게 한다.

**보안** — Athena SQL은 사용자 입력을 문자열 결합하지 않는다. 값은 파라미터화하고, 식별자
(테이블·컬럼·정렬 키)는 화이트리스트로만 허용한다(NFR-S-08).

## ADR-016. AI 어드바이저: Bedrock Converse + 구조화 출력 강제

**결정** — Bedrock Converse API로 Claude를 호출한다. 출력은 tool-use(스키마 강제)로 받는다.
리터럴은 기본적으로 보내지 않는다. Guardrail을 적용한다. 결과는 캐시한다.

**근거**
1. **구조화 출력 강제** — 자유 텍스트 응답은 파싱이 불안정하고 UI에 렌더하기 어렵다.
   **단 Bedrock Converse는 `toolSpec.inputSchema`를 모델 응답에 대해 검증하지 않고 자동
   재시도도 하지 않는다.** 잘못된 `toolUse.input`은 그대로 반환된다.
   → **앱이 JSON Schema로 검증하고, 실패 시 `toolResult`에 `status: "error"`와 위반 내용을
   담아 재요청한다**(최대 2회). 스키마는 모델에게 형식을 알려주는 역할이고 실제 강제는
   우리 코드가 한다. 초기 문서의 "모델이 재시도한다"는 사실이 아니었다.
2. **리터럴 미전송이 기본** — 슬로우 쿼리 원문에는 운영 데이터(주문번호, 이메일, 전화번호)가
   섞여 있다. `DIGEST_TEXT`(바인드 변수화된 형태)로도 인덱스 권고는 충분히 가능하다.
   선택도 판단에 실제 값이 필요한 경우가 있어 인스턴스별 옵트인을 남긴다(FR-AI-04).
3. **캐시 키에 스키마 지문 포함** — 같은 쿼리라도 인덱스가 바뀌면 권고가 달라져야 한다.
   `(app_digest, schema_fingerprint, mysql_version, prompt_version)`.
4. **`ANALYZE TABLE`을 실행하지 않는다** — 카디널리티를 정확히 하려는 유혹이 있지만
   InnoDB `ANALYZE TABLE`은 테이블 통계를 갱신하며 부하와 짧은 락을 유발한다. 관측 도구가
   대상을 건드리면 안 된다(FR-AI-10).
5. **캐시 키에 인스턴스·엔진 버전·플랜 지문을 포함한다.** 권고는 데이터 분포·인덱스 통계·
   옵티마이저 설정에 의존하므로, 인스턴스가 다르면 권고도 다를 수 있다.
   `(app_digest, instance_id, schema_fingerprint, engine_version, plan_fingerprint, prompt_version)`.
   → 캐시 히트율이 떨어지지만 정확성이 우선이다. 히트율 목표를 70% → 50%로 낮춘다.

**`STALE_STATS` 규칙의 근거가 틀렸다** — 초기 설계는 `information_schema.TABLES.UPDATE_TIME`이
30일을 넘으면 "통계가 낡았다"고 판정했다. **`UPDATE_TIME`은 마지막 데이터 변경 시각이지
통계 갱신 시각이 아니다.** 데이터가 30일간 안 바뀐 테이블은 통계도 정확할 가능성이 높다.

올바른 근거로 교체한다:
- `mysql.innodb_table_stats.last_update` / `mysql.innodb_index_stats.last_update` —
  **이게 실제 통계 갱신 시각**이다. 단 `mysql` 스키마 읽기 권한이 필요하다
  (권한 모드 A에서만 가능. 모드 B에서는 이 규칙을 비활성).
- 대체 신호: `CARDINALITY > TABLE_ROWS`(모순), `CARDINALITY = 0`인데 행이 있음,
  `innodb_stats_auto_recalc` 설정값 확인.
- 권한이 없으면 `STALE_STATS`를 발화하지 않고 "통계 신선도 확인 불가"로 표시한다.
  근거 없는 규칙을 사실로 제시하지 않는다.

**대가**
- 토큰 비용. → 캐시 + 월 예산 상한 + 자동 실행 옵션화.
- 모델이 틀린 인덱스를 권고할 수 있다. → 자동 적용 금지(FR-AI-09), 신뢰도와 검증 방법을
  출력에 포함, 사용자 피드백 수집(FR-AI-11).
- 프롬프트 변경이 결과 재현성을 깨뜨린다. → `prompt_version`을 결과에 저장.

## ADR-017. 리포트 수치는 모델이 만들지 않는다

**결정** — 리포트의 모든 수치는 Athena 집계 결과다. Bedrock은 그 수치를 **인용해 서술만** 한다.
프롬프트에 "제공된 수치 외의 숫자를 생성하지 말라"를 명시하고, 생성된 문장에 등장하는 숫자가
입력 집계에 존재하는지 후처리로 검증한다.

**근거** — 리포트는 의사결정 근거로 쓰인다. 모델이 그럴듯한 숫자를 만들면 신뢰가 한 번에
무너진다. 수치 검증은 자동화할 수 있으므로 안 할 이유가 없다.

**숫자 존재 검증만으로는 부족하다** — "입력에 있는 숫자인가"는 통과하지만
**"올바른 지표·기간·대상에 붙었는가"는 검증하지 못한다.**
`orders-prd-01의 P95가 210ms`를 `orders-prd-02의 평균이 210ms`로 잘못 서술해도 통과한다.

**대응 — 수치가 들어가는 문장은 LLM이 만들지 않는다.**

| 리포트 요소 | 생성 방식 |
|---|---|
| 표·차트 | Athena 결과 직접 렌더 (LLM 미개입) |
| 수치를 포함한 요약 문장 | **typed template**. 예: `"{instance}의 {metric}이 {before}에서 {after}로 {pct}% {direction}했다"` — 값은 코드가 바인딩 |
| 해설·맥락·권고 | LLM. **숫자를 쓰지 말라고 지시**하고, 숫자가 나오면 그 문장을 제거 |

즉 LLM의 역할을 "숫자를 인용해 서술"에서 **"숫자 없는 해설"** 로 좁힌다. 훨씬 안전하고,
검증기도 단순해진다(숫자 토큰이 0개인지만 확인).

**재현성에는 Iceberg 스냅샷 고정이 필요하다** — 같은 SQL을 재실행해도
늦게 도착한 데이터와 `MERGE INTO`로 인해 결과가 달라진다. Athena는 Iceberg 스냅샷 기반
시간 여행을 지원하므로, 리포트 생성 시 사용한 **스냅샷 ID를 메타에 기록**하고 재현 시
`FOR VERSION AS OF <snapshot_id>`로 조회한다.
스냅샷 만료 기간(관리형 유지보수)보다 오래된 리포트는 재현이 불가하므로,
**원본 집계 결과 JSON을 S3에 함께 저장**하는 것이 실질적 재현 수단이다(이미 설계에 있음).

**대가** — typed template을 리포트 섹션마다 작성해야 한다(15개 섹션). 서술이 딱딱해진다.
그 대가로 수치가 틀릴 수 없다. 리포트에서는 이 교환이 옳다.

## ADR-018. 샤딩: DynamoDB 조건부 쓰기 리스

**결정** — 워커가 인스턴스 샤드를 DynamoDB 조건부 쓰기로 임차한다(TTL 60초, 20초마다 갱신).
ZooKeeper/etcd/Consul을 도입하지 않는다. 1단계는 단일 워커로 시작하되 인터페이스는 리스 기반.

**근거**
- 이미 DynamoDB를 쓰고 있다. 조정 전용 인프라를 추가할 이유가 없다.
- 정확한 리더 선출이 필요한 게 아니다. 최악의 경우 두 워커가 같은 인스턴스를 잠깐 중복 수집
  하는데, 그건 폴링 쿼리 1건이 두 번 나가고 저장 시 같은 키로 덮어써질 뿐이다(멱등).
- 60초 리스면 워커 장애 시 최대 60초 수집 공백. NFR-R-02와 일치.

**⚠ 리스만으로는 split-brain을 막지 못한다** — "중복 수집이 잠깐 발생해도 안전하다"는 초기
주장은 틀렸다. 리스가 만료된 뒤에도 **이전 소유자의 늦은 쓰기가 도착할 수 있고**, 그것을
막는 장치가 없다. 구체적 피해:

| 데이터 | 중복 소유 시 무슨 일이 벌어지나 |
|---|---|
| SlowQuery | `record_id`가 초 단위로 정규화됐어도 두 워커의 시작 시각 추정이 1초 어긋나면 **레코드 2건**이 생긴다 |
| DigestRollup | 두 워커가 각자의 메모리 누산기를 갖는다. 정시 플러시가 last-writer-wins로 덮어써 **한쪽 누산분이 사라진다** |
| 다이제스트 델타 기준선 | 두 워커가 서로 다른 `LAST_SEEN` 체크포인트를 가져 구간이 중복·누락된다 |
| AlertState | 조건부 전이로 보호되지만, 늦은 쓰기가 `RESOLVED`를 되돌릴 수 있다 |

**대응 — 2단계로 나눈다.**

1. **1단계(현재): active collector 1대만 운영한다.**
   워커 여러 대를 띄우되 **standby**로 두고, 리더 리스를 잡은 1대만 수집한다.
   가용성은 "리스 TTL(60초) 안에 다른 워커가 인수"로 확보한다. 500대를 1대로 못 돌리게 되면
   그때 2단계로 간다. 이게 가장 게으르고 안전하다.
2. **2단계(샤딩 필요 시): 펜싱 토큰.**
   샤드마다 단조 증가 `epoch`를 발급하고, **그 샤드에 속한 모든 쓰기의 조건식에 포함**한다.
   ```
   ConditionExpression = "attribute_not_exists(lease_epoch) OR lease_epoch <= :my_epoch"
   ```
   리스를 새로 획득하면 `epoch`가 올라가므로 이전 소유자의 쓰기는 조건 실패로 거부된다.
   누산기 플러시도 `epoch`를 담아 조건부로 쓴다.

**대가**
- 1단계는 수집 처리량이 워커 1대에 묶인다. → NFR-P-01(500대)을 1대로 못 채우면
  2단계 펜싱 구현이 M12가 아니라 **선행 조건**이 된다. M1-9 벤치마크가 이걸 결정한다.
- 펜싱 토큰은 모든 쓰기 경로에 `epoch`를 전파해야 해서 코드가 침습적이다.
  그래서 필요해질 때까지 하지 않는다.
- 리스 갱신 실패(네트워크 순간 단절) 시 불필요한 재분배가 일어날 수 있다.
  → 갱신 실패 허용 횟수를 두고, 재분배는 점진적으로 한다.

**재검토 조건** — 워커가 20대를 넘으면 리스 경합이 늘어난다. 그때 샤드 할당을
일관 해싱 + 코디네이터 방식으로 전환.

## ADR-019. 지원 엔진 버전 하한

**결정** — RDS for MySQL **8.4 이상**, Aurora MySQL **3.x(MySQL 8.0.32 이상)**.
MySQL 5.7과 Aurora MySQL 2.x는 지원하지 않는다.

**맥락** — MySQL 5.7은 EOL이다. Aurora MySQL은 3.x가 MySQL 8.0 호환이므로 "8.4 이상"을
문자 그대로 적용하면 Aurora 인스턴스 대부분이 대상에서 빠진다.

**근거**
- 5.7 배제로 사라지는 분기: MD5 다이제스트(32자), `SHOW SLAVE STATUS`, `SHOW MASTER STATUS`,
  히스토그램 미지원, `EXPLAIN FORMAT=TREE` 미지원.
- 8.0.32를 하한으로 잡은 이유: `EXPLAIN FORMAT=JSON` 스키마가 안정화되고
  `SHOW REPLICA STATUS`(8.0.22+)가 이미 있으며, Aurora 3.x의 실사용 버전대가 여기 이상이다.
- 8.4에서 `SHOW SLAVE STATUS`가 **제거**되었으므로, 8.0.32+ 하한을 두면 `SHOW REPLICA STATUS`
  단일 경로로 8.0/8.4를 모두 커버한다. 버전 분기가 필요 없다.

**대가** — Aurora 3.x는 8.4 전용 기능(예: `explain_json_format_version=2`)을 못 쓴다.
→ 해당 기능은 사용하지 않거나, 버전 감지 후 선택적으로만 사용한다.

**⚠ 이 결정은 실사 없이는 확정할 수 없다** — 두 가지가 미확인이다.

1. **Aurora 버전 문자열은 순서 비교가 안 된다.** Aurora `EngineVersion`은
   `8.0.mysql_aurora.3.05.2` 형태다. `"8.0.32"`와 문자열·semver 비교가 불가능하다.
   더 중요하게 **Aurora 3.x ≠ MySQL 8.0.32+** 다 — Aurora 3.01~3.04는 커뮤니티
   8.0.23~8.0.28 기반이고, 8.0.32 대응은 3.05대부터다.
   → 게이팅은 `SELECT VERSION()`(커뮤니티 기반 버전 반환) 또는 Aurora→커뮤니티 매핑표로 한다.
   문서 표기도 **"Aurora MySQL 3.05 이상"** 처럼 Aurora 버전으로 쓴다.
   (`SHOW REPLICA STATUS`는 3.01(≈8.0.23) > 8.0.22이므로 결론 자체는 유지된다.)
2. **RDS MySQL 8.0은 사용 불가가 아니다.** 유료 Extended Support 상태이며, 이 프로젝트가
   쓰는 performance_schema 기능은 8.0에 모두 있다. "8.4+ 고정"은 **모니터 구축보다 큰
   업그레이드 프로젝트**를 선행 조건으로 만들 수 있다.

**따라서 순서를 바꾼다.** 하한을 확정하기 전에 **플릿 능력 인벤토리**를 먼저 한다
(M1-12). 실제 100대의 엔진·버전 분포를 뽑아 이 문서에 기록한 뒤:
- 8.4+ 비중이 높으면 → 현재 결정 유지
- 8.0.x가 다수면 → **기능 탐지 기반 축소 모드**를 지원한다. 즉 버전으로 배제하지 않고,
  자가진단이 "이 인스턴스에서 쓸 수 없는 기능"을 표시하고 나머지는 수집한다.
  8.0.32+에서 필요한 기능이 전부 되므로 실질 하한은 8.0.32다.
- Aurora 2.x가 남아 있으면 → 업그레이드가 프로젝트 선행 조건임을 명시한다.

**재검토 조건** — M1-12 인벤토리 결과. Aurora MySQL 8.4 호환 버전 GA 시점.

## ADR-020. S3 Tables 조회·처리는 Athena SQL 단독, Spark 미도입

**결정** — Iceberg 적재·조회·리포트 집계를 전부 Athena SQL로 한다.
EMR Serverless / Glue Spark / Athena for Apache Spark를 도입하지 않는다.

**맥락** — 사용자가 "s3table 조회를 위해 spark 같은거도 쓸수 있으면 좋을거 같긴해"라고 했고,
이후 "Athena 단독"으로 확정했다. 이 ADR은 그 결정의 근거를 남긴다.

**검토한 대안**

| 대안 | 상시 클러스터 | 판단 |
|---|---|---|
| **Athena SQL 단독** | 없음 | **채택** |
| Athena for Apache Spark | 없음 (세션 과금) | 기각. 노트북·PySpark가 필요한 작업이 현재 없다 |
| EMR Serverless | 없음 | 기각. 하루 1.2GB 변환에 Spark 런타임을 띄울 이유가 없다 |
| Glue Spark job | 없음 (DPU-시간) | 기각. 같은 이유 |
| EMR on EC2 | **있음** | 기각. 연 200GB 규모에 상시 클러스터는 명백한 과잉 |

**근거** — "상시 클러스터가 과잉"은 EMR on EC2에만 해당하는 논리이므로, 서버리스 Spark를
기각하려면 다른 근거가 필요하다. 실제 근거는 다음이다.

1. **작업이 SQL로 표현된다.** 일 1회 1.2GB를 `MERGE INTO` 하는 것과 월 1회 집계 15개.
   Spark의 이점(복잡한 변환, UDF, 반복 처리, ML 전처리)이 필요한 작업이 하나도 없다.
2. **비용이 자릿수로 싸다.** Athena 월 $6([16 §2.6](16-cost.md)) vs Spark 런타임 기동 비용.
3. **운영 대상이 0개 늘어난다.** Spark 잡은 의존성·버전·튜닝·실패 디버깅이 따라온다.
4. **팀 역량이 Rust·SQL이다.** Spark 역량을 새로 쌓을 이유가 없다.

**대가**
- 복잡한 백필·대규모 재적재를 SQL로만 표현해야 한다. 파티션 재작성 같은 작업이
  Athena 쿼리 여러 개로 쪼개질 수 있다.
- 이상 탐지·ML([17 부록 A](17-roadmap-tasks.md))을 도입하면 노트북 환경이 없다.
- 워크그룹 쿼리당 스캔 한도(10GB) 안에 모든 변환을 맞춰야 한다.
  → 아카이브 잡은 **전용 워크그룹**을 써서 한도를 별도로 설정한다.

**재검토 조건** — 다음 중 하나가 발생하면 **EMR Serverless / Athena for Apache Spark**를
재검토한다(상시 클러스터가 없으므로 위 기각 근거가 그대로 적용되지 않는다):
① Iceberg 볼륨 연 2TB 초과, ② `MERGE INTO` 소요가 스캔 한도·시간 예산을 넘김,
③ 이상 탐지·ML 기능 착수.

## ADR-021. 계정·호스트 축을 1급 데이터로 유지한다

**결정** — 슬로우 쿼리와 다이제스트에 `db_user` / `db_host`를 저장하는 것을 넘어,
**계정별 시간 롤업 엔티티**(`UR#`)를 두고 월간 리포트에 계정 섹션을 넣는다.
다이제스트 사전에 `seen_users` / `seen_hosts` 집합을 유지한다.

**맥락** — 1세대에는 "DB 계정별 월간 통계" 화면과 API가 있었다
(`apis/sql_statistics_api.py`, `components/UserStatisticsTable.tsx`).
2세대 초기 설계는 `db_user`를 저장·필터만 하고 집계 축에서 빼서, **1세대보다 후퇴**했다.

**근거** — "어느 쿼리가 느린가"보다 "**누가 그 쿼리를 돌리는가**"가 답을 못 하면 다음이
전부 막힌다.
- 알림을 어느 팀에 보낼지 (알림 스코프가 이미 `tags.team`을 지원하는데 연결 지점이 없다)
- noisy neighbor 식별 (배치 계정이 API 계정의 응답을 밀고 있는가)
- 워크로드 분리 판단 (리더로 보낼 계정, 커넥션 풀을 조여야 하는 계정)

**설계** — `DigestRollup`에 `by_user` 맵을 넣으면 카디널리티가 폭증한다.
별도 엔티티로 분리한다.
```
PK = UR#<instance_id>#<yyyy-mm>
SK = <hour_bucket>#<db_user>
속성: exec_count, total_time_ms, by_statement_type{SELECT,UPDATE,...}, slow_count
```
계정 수는 인스턴스당 수십 수준이므로 볼륨이 `DigestRollup`의 1% 미만이다.

**소스 확장** — 실시간 캡처·슬로우로그는 임계값 초과 쿼리만 본다.
`sys.user_summary_by_statement_type`과
`performance_schema.events_statements_summary_by_account_by_event_name`을 함께 수집하면
**임계값 미만 워크로드까지 계정별로 커버**한다(1세대에는 없던 개선).
이 테이블들은 [ADR-005](#adr-005-슬로우-쿼리-캡처-경량-탐지--타깃-심층-조회)의
자기 부하 계측에도 쓰인다.

**대가** — 엔티티 1개, 롤업 로직 1개, 리포트 섹션 2개가 늘어난다.
`db_user`가 애플리케이션마다 하나뿐인 조직에서는 가치가 낮다
→ 계정 수가 인스턴스당 2개 이하면 이 롤업을 자동 비활성한다(설정).

**재검토 조건** — 계정 축이 실제 조사에 쓰이지 않으면 롤업만 남기고 화면을 제거.
