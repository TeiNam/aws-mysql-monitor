# 미해결 이슈

두 종류가 있다.

- **검증 필요(V)** — 설계가 특정 동작을 전제하고 있고, 실측으로 확인해야 한다.
  대부분 [M1 검증 스파이크](17-roadmap-tasks.md#m1-검증-스파이크-매우-중요)에서 해소된다.
- **결정 대기(D)** — 정보가 더 필요하거나 사용자·조직 판단이 필요하다.

각 항목은 **왜 중요한가 / 어떻게 확인하는가 / 틀렸을 때 무엇이 바뀌는가**를 적는다.
해소되면 결과를 적고 관련 문서를 갱신한 뒤 `해소` 표시한다.

## OPEN-Q-01 (V) Rust 수집 루프가 실제로 500대를 커버하는가

**상태**: 미해소 · M1-9, M12-8

**왜** — [ADR-001](03-decisions.md)의 근거가 "다이제스트 파싱·정규화가 CPU 병목이 되므로
Python은 부족하다"는 것이다. 이건 추론이고 측정이 아니다. 만약 Python으로도 충분하다면
Rust 선택의 근거 하나가 사라진다(단일 바이너리·메모리 예측성은 남는다).

**어떻게** — 모의 MySQL 엔드포인트 하네스([15 §8.2](15-testing.md))로
인스턴스 100/250/500대, 다이제스트 행 500/2000개 조건에서
워커 CPU·메모리·tick 지연 p99를 측정한다.

**틀렸을 때** — 워커 1대가 125대를 못 커버하면 [02 §8](02-architecture.md)의 2단계
토폴로지에서 collector 대수를 늘리고 [16-cost.md](16-cost.md)의 컴퓨트 비용을 갱신한다.
반대로 훨씬 여유가 있으면 워커 수를 줄인다.

## OPEN-Q-02 (V/D) 크로스 리전 MySQL 폴링이 지연·비용 면에서 견디는가

**상태**: **현재 불필요** (2026-08-19 실측) · 검증을 M12로 연기

**실측 결과** — ap-northeast-2 외 3개 리전(us-east-1, ap-northeast-1, ap-southeast-1)에
RDS 인스턴스·Aurora 클러스터가 **0개**다. 멀티 리전은 미래 요구사항이다.

→ 멀티 리전 코드 경로(리전별 클라이언트 팬아웃)는 설계대로 만들되,
**지연·비용 검증은 실제 크로스 리전 대상이 생길 때까지 미룬다.**
[16 §2.9](16-cost.md)의 데이터 전송 비용도 현재는 동일 리전 기준으로만 계산하면 된다
(500대 × 7.1GB × $0.01 × 2방향 = $70이 아니라, 실제 대상 수만큼).

**원래 상태**: 미해소 · M1-10

**왜 (두 가지 이유)**

1. **지연** — 앱은 1개 리전에 배포되고 대상 RDS는 여러 리전에 있다. 왕복 지연이 폴링 주기의
   상당 부분을 먹으면 탐지 해상도가 떨어지고, 심층 조회(쿼리 3건 순차)가 예산을 초과한다.
2. **비용** — 폴링 트래픽은 무료가 아니다. 인스턴스당 월 약 7GB를 받으므로
   크로스 리전이면 인스턴스당 월 $0.15~0.65다([16 §2.9](16-cost.md)).
   150대가 크로스 리전이면 월 약 $53. 지연보다 이쪽이 결정을 더 강하게 밀 수 있다.

**어떻게** — 실제 리전 쌍(예: ap-northeast-2 ↔ us-east-1, eu-west-1)에서
TCP 왕복과 MySQL 쿼리 왕복을 측정한다. TLS 핸드셰이크 비용도 별도로 잰다.
동시에 실제 대상 인스턴스의 리전 분포를 조사해 크로스 리전 대수를 확정한다.

**결정해야 할 것** — 지연이 큰 리전을 (a) 폴링 주기 자동 상향으로 감당할지,
(b) 해당 리전에 collector를 배치할지. (b)를 택하면 리전별 배포·리스 파티셔닝·
DynamoDB 글로벌 테이블 여부까지 설계가 확장된다.

**현재 설계** — (a)를 기본으로 두고 왕복 500ms 초과 시 주기를 2초로 상향한다고 적어뒀다
([06 §4](06-discovery-metrics.md)). 측정 후 확정.

## OPEN-Q-03 (V) S3 Tables가 배포 리전에서 쓸 수 있고 Athena `MERGE INTO`가 동작하는가

**상태**: **대부분 해소** (2026-08-19 계정 123456789012 실측) · 남은 것은 M1-7

**실측 결과** ([18 §1.3](18-dev-environment.md))
- ap-northeast-2에서 **S3 Tables 사용 가능**. `dev-test-table-bucket-01`이 이미 존재하고
  네임스페이스 2개, 테이블 1개(`my_stock.news`)가 만들어져 있다.
- Glue에 `s3tablescatalog` 페더레이션 카탈로그가 **등록됨**.
- **카탈로그 이름 형식 확정**: `<account>:s3tablescatalog/<table-bucket-name>`
  → Athena 3파트 이름은 `"s3tablescatalog/<bucket>"."<namespace>"."<table>"`.
  검증 근거: `--catalog-id "123456789012:s3tablescatalog"` → 404,
  `--catalog-id "123456789012:s3tablescatalog/dev-test-table-bucket-01"` → 네임스페이스 반환.
- Athena **engine version 3** (Iceberg DML 지원).

**남은 것** — `MERGE INTO` / `DELETE` 실제 동작과 멱등성(2회 적재 후 행수 불변),
관리형 컴팩션·스냅샷 만료 설정, `s3tables:*` IAM 액션 이름.
이건 쓰기 작업이므로 `20-data` 레이어를 apply한 뒤 확인한다.

**원래 상태**: 미해소 · M1-7

**왜** — [ADR-004](03-decisions.md) 전체가 여기에 달렸다. 리전 미지원이면 콜드 티어 설계를
바꿔야 한다. 또 IAM 액션 이름(`s3tables:*`)과 Glue 카탈로그 연동 방식
(`s3tablescatalog` 등록)을 문서에서 추정으로 적었으므로 실제 API로 확인해야 한다.

**어떻게**
1. 배포 리전에서 S3 Tables 테이블 버킷 생성
2. Glue 카탈로그 통합 후 Athena에서 `CREATE TABLE ... TBLPROPERTIES('table_type'='ICEBERG')`
3. `INSERT INTO` / `MERGE INTO` / `DELETE` 동작 확인
4. 같은 데이터를 2회 `MERGE` → 행수 불변 확인
5. 실제 IAM 액션 이름 확인 (거부 시 CloudTrail에서 요구 액션 확인)
6. 관리형 컴팩션·스냅샷 만료 설정 확인

**틀렸을 때** — 플레인 S3 Parquet + Glue Hive 파티션으로 전환한다. 그 경우 추가로 필요한 것:
- 소파일 컴팩션 잡 (Athena CTAS, 주 1회)
- 백필 시 파티션 재작성 잡
- 보관 만료는 S3 Lifecycle (더 단순해짐)
- `MERGE` 대신 "덮어쓸 파티션을 CTAS로 재생성" 패턴
→ [ADR-004](03-decisions.md)의 "차선" 항목을 채택으로 승격하고 [04](04-data-model.md),
[14](14-infrastructure.md), [17](17-roadmap-tasks.md) M7을 갱신한다.

## OPEN-Q-04 (D) 워커 다중화 시 실시간 이벤트 팬아웃을 어떻게 하는가

**상태**: 미해소 · M12-6. **1단계에서는 문제가 되지 않는다**(단일 워커 또는 API 역할 통합).

**왜** — 2단계 토폴로지에서 collector 워커와 API 워커가 분리되면, 슬로우 쿼리 확정 이벤트와
실시간 지표가 collector 워커의 메모리에 있고 클라이언트는 API 워커에 붙어 있다.
그 사이를 연결해야 한다.

**후보**

| 방식 | 장점 | 단점 |
|---|---|---|
| API 역할을 collector와 통합 유지 | 추가 인프라 0 | 확장 축이 묶인다. ALB 스티키로 특정 인스턴스 데이터를 가진 워커에 붙일 수 없다 |
| DynamoDB Streams → API 워커가 구독 | 인프라 추가 없음(이미 DynamoDB 사용) | 지연 수백 ms~수 초. 실시간 지표(5초 해상도)에는 부적합. 스트림 소비자 관리 필요 |
| Redis(ElastiCache) pub/sub | 지연 수 ms, 단순 | 인프라 추가 (월 약 $30~60), 장애 지점 추가 |
| SNS/EventBridge | 관리형 | 지연·비용, 팬아웃 대상 등록 관리 |
| collector 워커가 API 워커에 직접 gRPC 푸시 | 지연 최소 | 서비스 디스커버리 필요 |
| 실시간 지표를 API 워커가 직접 수집 | 팬아웃 불필요 | 대상 DB에 수집 주체가 둘이 됨(부하 2배) — 기각 |

**현재 기울기** — Redis pub/sub. 이유: 실시간 지표는 지연이 핵심이고, DynamoDB Streams는
그 용도에 맞지 않는다. 월 $30~60은 이 시스템 총비용($600) 대비 수용 가능하다.
단 **500대에 도달할 때까지 결정을 미룬다.** 그때 실제 워커 수와 클라이언트 수를 보고 정한다.

**대안 완화** — 실시간 지표만 Redis로 보내고, 슬로우 쿼리·알림 이벤트는
DynamoDB Streams로 처리하는 혼합도 가능하다(후자는 초 단위 지연이 허용됨).

## OPEN-Q-05 (V) `EXPLAIN FORMAT=TREE FOR CONNECTION`이 지원되는가 — **해소**

**상태**: **해소** (2026-08-20 실측, [19 §B](19-m1-findings.md))

**결과** — MySQL 8.4.11 에서 `FORMAT=TREE FOR CONNECTION` 이 **지원된다.**
SELECT·UPDATE·DELETE·`INSERT ... SELECT` 모두 결과를 반환했다. `FORMAT=TRADITIONAL` 도 된다.

**단 이 질문의 실효성이 사라졌다** — `FOR CONNECTION` 자체가 RDS 에서 쓸 수 없기 때문이다
([OPEN-Q-06](#open-q-06-v-데이터-select-권한-없이-explain-for-connection이-되는가) 참조).
`FORMAT=TREE` 는 사후 재실행 경로에서 얻는다(권한 문제 없음).

**원래 상태**: 미해소 · M1-3

**왜** — [05 §2.4](05-collector.md)에서 JSON은 확실하다고 보고 TREE는 "버전별 확인 필요"로
적었다. TREE 형식은 사람이 읽기 훨씬 쉬워서 UI 가치가 크다.

**어떻게** — MySQL 8.4와 8.0.32 컨테이너에서 장기 실행 쿼리를 만들고
`EXPLAIN FORMAT=TREE FOR CONNECTION <id>`를 실행해 결과·에러를 기록한다.
`FORMAT=TRADITIONAL FOR CONNECTION`도 함께 확인한다.

**틀렸을 때** — in-flight에서는 JSON만 수집하고, TREE는 사후 폴백 경로(SELECT 재실행)에서만
얻는다. UI는 정규화된 플랜 트리(백엔드가 JSON에서 생성)를 기본 표시로 하고
TREE 텍스트는 있을 때만 탭으로 제공한다.

## OPEN-Q-06 (V) 데이터 `SELECT` 권한 없이 `EXPLAIN FOR CONNECTION`이 되는가 — **해소(부정)**

**상태**: **해소** (2026-08-20 실측, [19 §B](19-m1-findings.md)). **ADR-006 이 깨졌다.**

**결과** — 질문의 전제 자체가 틀렸다. `SELECT` 권한이 있어도 **타인 커넥션은 explain 할 수 없다.**
필요한 것은 **정적 전역 권한 전체**이고, RDS 는 마스터 유저에게도 `SUPER`·`FILE`·`SHUTDOWN` 을
주지 않는다. `PROCESS` 도 `SUPER` 도 부족하다. 대상 테이블이 없는 문장(`SELECT SLEEP(20)`)에서도
같은 결과이므로 테이블 권한 문제가 아니다.

→ 권한 모드 C(`minimal`)를 도입할 이유가 없어졌다. 모드 B(`least`)가 기본이며,
플랜은 **사후 재실행**으로 얻는다(`SELECT` 권한만 필요).
DML 은 조건절을 `SELECT` 로 바꿔 근사 플랜을 얻는다(`ERROR 1142` 회피).

**원래 상태**: 미해소 · M1-4

**왜** — 사실이면 모니터링 계정에 운영 데이터 읽기 권한을 **전혀 주지 않고도** 플랜을 얻을
수 있다. 보안상 큰 차이다([07 §2.3](07-credentials-bootstrap.md) 모드 C).
`EXPLAIN FOR CONNECTION`은 이미 만들어진 플랜을 읽는 것이므로 테이블 권한 검사가 없을
가능성이 있지만, MySQL이 실제로 어떻게 구현했는지는 확인해야 한다.

**어떻게**
```sql
-- 최소 권한 계정 생성
CREATE USER 'minimal'@'%' IDENTIFIED BY '...';
GRANT PROCESS, REPLICATION CLIENT, SHOW DATABASES, SHOW VIEW ON *.* TO 'minimal'@'%';
GRANT SELECT ON performance_schema.* TO 'minimal'@'%';
GRANT SELECT ON sys.* TO 'minimal'@'%';
-- 데이터 스키마 SELECT 없음

-- 다른 세션에서 shop.orders 를 읽는 장기 쿼리 실행
-- minimal 계정으로 EXPLAIN FORMAT=JSON FOR CONNECTION <id> 실행
```
- 플랜이 나오는가?
- 플랜 안에 컬럼명·조건식(`attached_condition`)이 보이는가? (보인다면 **스키마 정보가
  권한 없이 노출되는 것**이므로 그 자체로 검토가 필요하다)
- `information_schema.PROCESSLIST`에서 다른 계정의 `INFO`(SQL 전문)가 보이는가?
  (`PROCESS` 권한으로 보이는 것이 정상)

**사실일 때** — 모드 C(`minimal`)를 도입한다. 평상시는 데이터 읽기 권한 0,
어드바이저 실행 시에만 별도 계정(`dbmon_advisor`)을 쓰는 2계정 구성을 M10에 추가한다.
[07](07-credentials-bootstrap.md), [08](08-security-auth.md) 갱신.

**아닐 때** — 모드 B(`least`, 스키마 화이트리스트)를 기본으로 확정한다. 현재 설계 유지.

## OPEN-Q-07 (V) `information_schema.PROCESSLIST.INFO`가 정말 절단되지 않는가 — **해소(부분)**

**상태**: **해소** (2026-08-20 실측, [19 §A](19-m1-findings.md))

**결과** — **절단된다. 단 65,535바이트에서다.**
컬럼 타입이 `varchar(21845)` 이고 `LONGTEXT` 가 아니다(21845 × 3바이트 = 65535).
`performance_schema.processlist.INFO` 는 `longtext` 이지만 내용이 1,024바이트로 잘린다 —
두 컬럼의 제약 방향이 반대다.

| SQL 길이 | PS `processlist` | IS `PROCESSLIST` | `events_statements_current` |
|---|---|---|---|
| 4,097 | 1,024 | 4,097 | 1,024 |
| 16,387 | 1,024 | 16,387 | 1,024 |
| 65,541 | 1,024 | **65,535** | 1,024 |
| 1,048,577 | 1,024 | **65,535** | 1,024 |

→ ADR-005 는 **유효**하다(64배 개선). 다만 65KB 초과 시 `sql_text_truncated=true` 를 세운다.
폴백(`performance_schema_max_sql_text_length` 상향)도 동작을 확인했다(1024 → 8192).

**원래 상태**: 미해소 · M1-1. **[ADR-005](03-decisions.md)의 핵심 전제**

**왜** — 1세대의 실제 버그(1024바이트 절단)를 고치는 방법이 이것이다. 만약
`information_schema.PROCESSLIST`도 어떤 한도에서 잘린다면 다른 경로가 필요하다.

**어떻게**
```
1. 4KB, 16KB, 64KB, 1MB 길이의 SELECT 문을 만들어 오래 실행시킨다
   (예: 매우 긴 IN 절 + 느린 조인)
2. performance_schema.processlist.INFO 길이 측정 → 1024 예상
3. information_schema.PROCESSLIST.INFO 길이 측정 → 원본과 같아야 함
4. events_statements_current.SQL_TEXT 길이 측정 → performance_schema_max_sql_text_length 예상
5. RDS 파라미터 그룹에서 performance_schema_max_sql_text_length=8192 설정 후 재부팅해
   4번을 재측정 (폴백 경로 검증)
```

**틀렸을 때** — 폴백: 파라미터 그룹에서 `performance_schema_max_sql_text_length`를 올리고
`events_statements_current.SQL_TEXT`를 전문 소스로 쓴다. 재시작이 필요하므로
[ADR-005](03-decisions.md)의 "재검토 조건"이 기본 경로가 된다.
그 경우 자가진단에 "이 파라미터가 낮으면 SQL이 잘립니다" 경고를 필수로 추가하고,
잘린 레코드는 `sql_text_truncated=true`로 명확히 표시한다.

## OPEN-Q-08 (D) SQL 텍스트 검색을 어떻게 제공하는가

**상태**: 미해소 · M12-12

**왜** — "이 테이블을 참조하는 슬로우 쿼리 찾기", "이 힌트를 쓴 쿼리 찾기"는 실무에서 자주
필요하다. DynamoDB는 전문 검색을 못 한다([ADR-003](03-decisions.md)의 대가).

**후보**

| 방식 | 장점 | 단점 |
|---|---|---|
| Athena `LIKE`/`regexp_like` (Iceberg) | 인프라 추가 0. 이미 있는 경로 | 최근 31일은 아카이브에 아직 없거나 하루 지연. 비동기 조회 |
| `referenced_tables` 배열 필드로 테이블 검색만 지원 | 매우 저렴. 가장 흔한 요구를 커버 | 임의 텍스트 검색 불가 |
| OpenSearch 추가 | 강력 | 클러스터 운영 + 월 $100+ |
| DynamoDB에 n-gram 역색인 직접 구축 | 인프라 추가 0 | 쓰기 비용 폭증. 기각 |

**현재 기울기** — 2단계로 간다.
1. **`referenced_tables` 기반 필터** (M4에 이미 저장하므로 GSI 또는 필터로 제공) —
   "이 테이블 쓰는 쿼리" 요구의 대부분을 커버한다.
2. **임의 텍스트 검색은 Athena 경로** (`slow_query_text_search` 쿼리 타입, 이미 [13 §2.9](13-api-spec.md)에
   enum으로 정의). 최근 데이터가 아카이브에 없는 문제는 "최근 31일은 DynamoDB를 스캔"으로
   해결하되, 기간을 제한(최대 7일)해 비용을 통제한다.

OpenSearch는 위 둘로 부족하다는 피드백이 실제로 나온 뒤에 검토한다.

## OPEN-Q-09 (D) 샤드 불균형을 어떻게 다루는가

**상태**: 미해소 · M12-10

**왜** — `hash(instance_id) % 64` 방식은 샤드별 인스턴스 수가 다를 수 있고, 더 중요하게는
**인스턴스별 부하가 다르다**(슬로우 쿼리가 많은 인스턴스, 다이제스트가 수천 개인 인스턴스).
한 워커가 무거운 인스턴스를 몰아서 받으면 tick이 밀린다.

**후보**
- 샤드 수를 늘린다(64 → 256). 평균화 효과. 리스 항목이 늘어나는 대가.
- 실측 부하(다이제스트 행 수, 슬로우 쿼리 빈도)로 가중치를 계산해 인스턴스를 개별 할당한다.
  리스 단위를 샤드가 아니라 인스턴스로 바꾸면 500개 리스가 되지만 DynamoDB에는 부담이 없다.
- 워커가 자기 tick 지연을 보고 과부하 시 샤드를 자발적으로 반납한다(부하 기반 자율 조정).

**현재 기울기** — 세 번째(자율 반납)가 가장 단순하고 적응적이다. tick 지연 p95가 폴링 주기의
70%를 넘으면 가장 무거운 샤드 1개를 반납한다. 다른 워커가 받아간다. 진동을 막기 위해
반납 후 5분 쿨다운.

**결정 시점** — M12-8 부하 테스트에서 실제 불균형 정도를 본 뒤.

## OPEN-Q-10 (V) IAM DB 인증 활성화에 재부팅이 필요한가

**상태**: 미해소 · M1-5

**왜** — [07 §2.1](07-credentials-bootstrap.md)에서 "재부팅이 필요할 수 있다"고 보수적으로
적었다. 프로덕션 RDS 재부팅은 다운타임이므로, 필요한지 아닌지가 절차와 사용자 문구를 바꾼다.

**결과 반영** — [07 §2.1](07-credentials-bootstrap.md)의 UI 문구를 확정하고,
필요하면 "재부팅 필요" 배지와 절차 안내를 추가한다.
**어느 경우든 우리가 재부팅을 실행하지는 않는다.**

## OPEN-Q-11 (D) 쿼리 KILL 기능을 제공할 것인가

**상태**: 미해소. 현재 [01 §2](01-requirements.md)에서 **비목표**로 선언

**왜** — 락 대기 화면을 보면 "지금 이걸 죽이고 싶다"는 요구가 반드시 나온다.
`sys.innodb_lock_waits`는 `sql_kill_blocking_query` 컬럼으로 명령까지 준다.

**찬성** — 장애 대응 속도. 이미 블로킹 체인을 화면에 보여주고 있으니 한 걸음이다.

**반대**
- 관측 도구가 대상을 변경하는 순간 성격이 달라진다. 오작동의 대가가 서비스 장애다.
- `KILL` 권한(`CONNECTION_ADMIN` 또는 `PROCESS` + RDS의 `rds_kill_query` 프로시저)이
  필요해져 모니터링 계정의 최소 권한 원칙이 깨진다.
- 누가 무엇을 죽였는지에 대한 감사·승인 절차가 새로 필요하다.

**현재 설계** — 명령을 **표시만** 한다([14 §8.7](14-infrastructure.md)).
사람이 복사해서 실행한다. 이게 안전과 편의의 합리적 지점이다.

**제공하기로 한다면 필요한 것** — 별도 IAM 정책·별도 DB 계정, admin 전용, 대상 정보와
확인 타이핑, 감사 로그, prd에서는 2차 확인. M12 이후 별도 마일스톤으로 다룬다.

## OPEN-Q-12 (D) Aurora MySQL 8.4 호환 버전 대응 — **해소**

**상태**: **해소** (2026-08-19 실측). [ADR-019](03-decisions.md)

**실측 결과** — 계정 123456789012의 **전 리전에 RDS 인스턴스와 Aurora 클러스터가 0개**다
(ap-northeast-2 / us-east-1 / ap-northeast-1 / ap-southeast-1 확인).

→ **8.4+ 고정이 대규모 DB 업그레이드 프로젝트를 선행 조건으로 만들 위험이 없다.**
모니터링 대상을 새로 만들면 되고, 그때 8.4로 만든다([18 §5](18-dev-environment.md)).
Aurora 2.x 잔존 문제도 없다. ADR-019의 우려는 이 계정에서 성립하지 않는다.

**남는 것** — 나중에 다른 계정·조직의 기존 인스턴스를 대상에 넣을 때 이 질문이 다시 유효해진다.
그때 [17](17-roadmap-tasks.md) M1-12(플릿 능력 인벤토리)를 다시 실행한다.
Aurora 버전 문자열 파싱 로직(`8.0.mysql_aurora.3.05.2` → 3.05)은 그대로 필요하다.

**원래 상태**: 부분 결정

**결정된 것** — RDS MySQL은 8.4+, Aurora MySQL은 3.x(8.0.32+)를 하한으로 한다.
8.0.32+ 하한이면 `SHOW REPLICA STATUS` 단일 경로로 8.0/8.4를 모두 커버하므로
버전 분기가 거의 없다.

**남은 것**
- 사용 리전에서 Aurora MySQL 8.4 호환 버전(버전 4)의 가용 여부와 시점
- `SHOW BINARY LOG STATUS`(8.4) vs `SHOW MASTER STATUS`(8.0) — 이 하나는 분기가 필요하다
  ([05 §2.7](05-collector.md)). 실제로 바이너리 로그 위치가 필요한 기능이 있는지 재검토
  (없으면 이 분기 자체를 제거할 수 있다)
- 대상 인스턴스 중 Aurora MySQL 2.x가 남아 있는지 실사

**액션** — M2-6 구현 시 실제 인스턴스 목록의 버전 분포를 뽑아 이 문서에 기록한다.
2.x가 상당수면 업그레이드가 이 프로젝트의 선행 조건임을 명시해야 한다.

## OPEN-Q-15 (D) prd 리터럴 저장 정책 — 조직 결정 필요

**상태**: 미해소 · **사용자 결정 대기**. [08 §6.1](08-security-auth.md)

**무엇이 걸려 있는가** — 이 프로젝트의 대표 기능(FR-DGS-06 "복사해서 바로 실행할 수 있는
샘플 쿼리")이 prd에서 켜지는지 꺼지는지가 이 결정에 달렸다. **튜닝이 필요한 쿼리는 대부분
prd에 있다.**

**현재 설계** — prd 기본값을 `full_restricted`로 정했다.
저장은 원문으로 하고, 조회를 operator 이상 + 감사 로그로 통제한다.

| 정책 | 저장 | 조회 | 샘플 실행 가능? | 되돌릴 수 있나? |
|---|---|---|---|---|
| `full` | 원문 | `can_see_literals` 권한에 따름 | ✓ | — |
| **`full_restricted`** (현재 기본) | 원문 | operator 이상 + 감사 | ✓ | ✓ (권한만 조이면 됨) |
| `masked` | `?` 치환 | 누구나 | ✗ | **✗ (영구 손실)** |
| `off` | 미저장 | — | ✗ | ✗ |

**근거** — 저장 시점 마스킹은 되돌릴 수 없고, 노출 시점 통제는 되돌릴 수 있으면서 동등하게
안전하다(응답 직렬화 계층에서 강제하므로 새 엔드포인트에서 빠뜨릴 수 없다).

**확인이 필요한 것**
1. 조직 규정상 **운영 데이터 리터럴을 이 시스템에 저장해도 되는가?**
   카드 정보·의료 정보·개인정보 처리 위탁 범위 밖 데이터가 SQL에 들어가는가?
2. 들어간다면 스키마·테이블 단위로 제외할 수 있는가(그러면 나머지는 `full_restricted` 가능)?
3. 저장 자체가 불가하면 `masked`로 바꾸고, **다이제스트 상세에 "실행 가능한 샘플 제공 불가"를
   명시**한다. `QUERY_SAMPLE_TEXT`(PS 샘플)도 리터럴을 포함하므로 함께 마스킹해야 한다.

## OPEN-Q-16 (V) `DIGEST_TEXT` 절단이 `DIGEST` 해시도 바꾸는가 — **해소(바꾼다)**

**상태**: **해소** (2026-08-20 실측, [19 §E](19-m1-findings.md))

**결과** — **해시가 달라진다.** 3,330바이트 SQL(서로 다른 식별자 300개):

| `max_digest_length` | `DIGEST_TEXT` 길이 | `DIGEST` |
|---|---|---|
| 1,024 | 958 | `61416d954598164e…` |
| 4,096 | 3,826 | `033f75ac13c2b45a…` |

→ `app_digest` 는 **필수**다. [ADR-011](03-decisions.md) 유지. 자체 lexer 부담이 남는다.

**⚠ 두 변수를 혼동하면 반대 결론이 나온다.** `performance_schema_max_digest_length` 만
올리면 해시가 같게 나온다(첫 측정에서 실제로 그랬다). 해시를 바꾸는 것은
**`max_digest_length`** 다. 자가진단이 읽는 변수를 정정했다([05 §9](05-collector.md)).

부수 발견: 절단된 `DIGEST_TEXT` 는 `...` 로 끝나지 **않는다**. 토큰 중간에서 그냥 끝난다.

**원래 상태**: 미해소 · M1-6과 함께 검증

**왜** — [ADR-011](03-decisions.md)이 "파라미터 그룹이 다른 인스턴스 사이에서는 긴 쿼리의
`mysql_digest`가 달라진다"를 전제로 `app_digest`를 도입했다. 하지만 **절단이 텍스트만 자르는지
해시 계산 대상 토큰 스트림까지 자르는지** 확인하지 않았다.

**어떻게**
```
1. 두 컨테이너를 서로 다른 max_digest_length (1024 / 4096) 로 기동
2. 절단 길이를 넘는 동일한 긴 쿼리를 양쪽에서 실행
3. DIGEST(해시)와 DIGEST_TEXT를 비교
   - 해시가 같다  → mysql_digest 를 크로스 인스턴스 키로 쓸 수 있다
   - 해시가 다르다 → app_digest 가 필수 (현재 설계 유지)
4. STATEMENT_DIGEST(sql) 함수 결과도 같은 방식으로 비교
```

**해시가 같다면** — `app_digest`의 역할이 크게 줄어든다. 크로스 인스턴스 그룹핑도
`mysql_digest`로 하고, 자체 정규화는 **마스킹**과 **CloudWatch 슬로우로그 보강**에만 쓴다.
자체 lexer의 정확성 부담이 사라지므로 큰 이득이다.
→ [ADR-011](03-decisions.md), [05 §3](05-collector.md), [15 §3.1](15-testing.md) 갱신.

## OPEN-Q-17 (V) IAM DB Auth가 대상 인스턴스 메모리를 얼마나 쓰는가

**상태**: 미해소 · M1-5와 함께 검증

**왜** — AWS는 IAM 인증 사용 시 인스턴스에 수백 MiB 수준의 여유 메모리를 확보하라고
안내한다. `db.t3.micro`·`db.t4g.small` 같은 작은 인스턴스에서 이건 무시할 양이 아니고,
**관측 도구가 관측 대상의 가용 메모리를 잠식하는** 상황이 된다.

**어떻게** — dev 환경의 작은 인스턴스(`db.t4g.small`)에서 IAM 인증 활성화 전후의
`FreeableMemory`를 비교한다. 연결 수를 늘려가며(1 → 3 → 10) 증가 추이도 본다.

**결과 반영** — 인스턴스 클래스별 정책을 설정으로 둔다.
예: `db.t*` 계열은 기본 비밀번호 방식, `FreeableMemory`가 임계 미만이면 부트스트랩 계획
단계에서 경고 + 비밀번호 방식 권고([ADR-007](03-decisions.md)).

## OPEN-Q-18 (V/D) Cognito access token의 `cognito:groups` 주입 방법

**상태**: 미해소 · M5-1과 함께 확인. [08 §2.3](08-security-auth.md)

**왜** — 설계가 (a) **access token으로 인가**하고 (b) IdP 그룹을 **Pre Token Generation
트리거로 `cognito:groups`에 주입**한다고 했다. 그런데 **트리거 V1의 `groupOverrideDetails`는
ID 토큰에만 적용된다.** access token 클레임 커스터마이즈는 **트리거 V2**가 필요하고,
V2는 상위 기능 요금제(Essentials/Plus)를 요구한다.

**후보**

| 방안 | 장점 | 단점 |
|---|---|---|
| **최초 로그인 시 실제 그룹 멤버십 부여** (`AdminAddUserToGroup`) | 네이티브 그룹 멤버십은 access token의 `cognito:groups`에 그대로 나온다. 요금제 무관 | Post Authentication 트리거 또는 첫 API 호출 시 동기화 로직 필요. 그룹 변경이 즉시 반영되지 않을 수 있음 |
| Pre Token Generation **V2** | 매 토큰 발급 시 최신 매핑 반영 | 상위 요금제 필요. 비용 확인 필요 |
| ID 토큰으로 인가 | V1으로 충분 | 만료·스코프 의미가 어긋난다([ADR-012](03-decisions.md)에서 기각한 이유) |

**현재 기울기** — 첫 번째. 어차피 [08 §3](08-security-auth.md)에서 **서버 측 `USER` 레코드와
교집합**하도록 바꿨으므로, 토큰의 그룹 클레임은 보조 신호다. `USER` 레코드가 권위값이면
`cognito:groups`가 비어 있어도 동작한다 → **트리거 자체가 불필요할 수도 있다.**

**확인 사항** — `USER` 레코드만으로 인가하면 (a) 토큰 클레임에 의존하지 않아 T-20이 원천
차단되고, (b) Lambda·요금제 문제가 사라진다. 대신 admin이 사용자를 명시적으로 등록해야 한다
(승인 대기 목록). 사용자 수십 명 규모에서는 이게 오히려 낫다.
→ M5-1에서 결정한다. 결정하면 [08 §2.3](08-security-auth.md)의 Lambda 절을 제거하거나 축소.

## OPEN-Q-19 (D) `UpdateUserPoolClient`를 앱에 줄 것인가

**상태**: 미해소 · M5-1 / M9. [08 §5.1](08-security-auth.md)

**왜** — IdP를 UI에서 추가하려면 `CreateIdentityProvider` 후
`UpdateUserPoolClient`의 `SupportedIdentityProviders`에 추가해야 한다.
그런데 이 API는 **App Client 전체**를 변경할 수 있어, 침해 시 콜백 URL을 추가해
토큰 탈취 리다이렉트를 심을 수 있다(T-27).

**후보**
- **Terraform 관리** — IdP 추가가 드물면(연 수 회) 이게 낫다. 앱은 IdP 목록 조회만.
  FR-AUT-04("IdP 등록을 관리자 UI에서")를 부분 포기.
- **`dbmon-auth-admin-role` 분리** — 이미 설계했다. 15분 세션 + ExternalId.
  UI 편의는 유지하되 상시 권한이 아니다.
- **콜백 URL 변경만 별도 통제** — API 레벨에서 분리가 불가하므로 실현 불가.

**현재 기울기** — 두 번째(별도 Role). 단 IdP 추가 빈도가 연 2회 미만이면 Terraform으로
옮기는 것이 명백히 낫다. M5-1에서 실제 IdP 개수와 추가 빈도를 확인해 결정한다.

## OPEN-Q-20 (D) `instance_id`에 계정 ID를 포함할 것인가 — **구현 착수 전 마지막 기회**

> **해소 (2026-08-19, M0-2a)**: `instance_id = <account_id>/<region>/<identifier>` 로 확정했다.
> `crates/core/src/ids.rs` 가 구현하고 `InstanceId::parse` 는 **2성분 형식을 거부한다.**
> 문서 전체의 예시도 3성분으로 통일했다. 근거: `dbmon-data` 는 여러 계정의 인스턴스를 한
> 테이블에 담고, 인스턴스 이름은 계정 안에서만 유일하다. 계정이 빠지면 서로 다른 계정의
> 동명 인스턴스가 같은 파티션 키를 갖는다. 비용은 키 길이(≈45자)뿐이다.

**상태**: **해소** (2026-08-19, M0-2a) · **M0-2 전에 결정해야 한다.** [02 §10](02-architecture.md), [04 §1](04-data-model.md)

**왜 지금 결정해야 하는가** — `instance_id`는 **모든 파티션 키에 들어간다.**
현재 형식은 `<account>/<region>/<identifier>`이고, 멀티 계정으로 확장하려면
**1차 키 포맷 변경 + 전 데이터 마이그레이션**이 필요하다. `account_id` 파라미터를 추가하는
문제가 아니다(초기 설계의 확장 지점 표는 이걸 잘못 표현했다 — F18).

서로 다른 계정에 같은 리전·같은 식별자가 존재하는 것은 흔하다(`prod-db-01`이 두 계정에 있는 등).
그러면 키가 충돌해 두 계정 데이터가 한 파티션에 섞인다.

**선택**

| 방안 | 지금 비용 | 나중 비용 |
|---|---|---|
| `<account>/<region>/<identifier>` 유지 | 0 | 멀티 계정 시 키 포맷 변경 + 전 데이터 마이그레이션 |
| **`<account>/<region>/<identifier>`** | 키가 13자 길어진다. 문서 예시 전면 수정 | **0** |

**권장: 계정 포함.** 단일 계정에서는 계정 ID를 고정값으로 넣으면 되고, 비용은
"키가 조금 길어진다"뿐이다. 저장량 증가는 항목당 13바이트 × 96M 항목 = 1.2GB(전체의 2%).

**부수 변경 (계정 포함을 택해도 남는 것)** — 멀티 계정 실행 시에는 여전히 다음이 필요하다:
IAM `dbuser:*/dbmon` 리소스를 계정별로, 크로스 계정 슬로우로그 로그 그룹 접근,
KMS 키 정책, `sts:AssumeRole` 세션 계층. 이건 키 포맷과 무관하게 그때 하면 된다.

**결정하지 않으면** — 문서 전체가 `<account>/<region>/<identifier>` 예시로 쓰여 있으므로 그대로 구현되고,
멀티 계정이 필요해지는 순간 마이그레이션 프로젝트가 된다.

## OPEN-Q-21 (D) dev/prd 토폴로지 차이로 검증할 수 없는 것을 어디서 확인하는가

**상태**: **해소** (2026-08-19, M0-2a) · M12. [18 §4](18-dev-environment.md)

**왜** — dev는 비용 때문에 ALB·NAT·WAF·인터페이스 엔드포인트를 만들지 않고
**퍼블릭 서브넷 + SSM 포트 포워딩**으로 접근한다(네트워크 비용 $0).
그 대가로 prd에서만 존재하는 다음 4개를 dev에서 검증할 수 없다.

| 검증 불가 항목 | prd에서 무엇이 달라지는가 |
|---|---|
| ALB 헬스체크·등록 해제 지연·유휴 타임아웃·WS 업그레이드 | 무중단 배포와 WS 재연결이 dev에서 한 번도 안 돌아본 경로다 |
| WAF 관리형 규칙 | 부트스트랩 POST가 SQL 인젝션 규칙에 걸리는지(T-30) 모른다 |
| VPC 인터페이스 엔드포인트 경유 시 IAM 조건 (`aws:SourceVpce`) | 정책을 좁히면 prd에서만 거부될 수 있다 |
| 프라이빗 서브넷 DNS 해석·NAT 경유 지연 | `AF_NETLINK` 하드닝 함정(14 §3.3)이 dev에서 드러나지 않는다 |

**후보**

| 방안 | 비용 | 커버리지 |
|---|---|---|
| **dev에 ALB 레이어를 임시로 apply → 검증 → destroy** | ALB 시간당 $0.0225 (하루 $0.5) | ALB·WAF 커버. 레이어가 독립이므로 쉽다 |
| 스테이징 환경 신설 (prd와 동일 토폴로지) | 월 $150+ | 전부 커버. 가장 비싸다 |
| prd 첫 배포를 "검증 배포"로 취급 (대상 0개로 띄우고 확인) | $0 | 전부 커버. 대신 prd에서 처음 실패를 본다 |

**현재 기울기** — 첫 번째 + 세 번째 조합.
① M12에서 dev에 `40-compute`를 ALB 포함으로 하루 apply해 ALB·WAF·엔드포인트 조건을 확인하고
destroy한다(비용 $1 미만). ② prd 첫 배포는 수집 대상 0대로 띄워 프라이빗 서브넷 경로만
확인한 뒤 인스턴스를 붙인다. 스테이징 상설은 이 규모에서 과잉이다.

**결정 시점** — M12. 그전에는 dev 토폴로지 차이를 [18 §4](18-dev-environment.md)에 명시해 둔다.
